Testing — strategies

Strategy in one sentence

Put the most tests where failures are cheapest to find and fix, and reserve slow, brittle checks for a thin layer at the top. Your strategy should match how the system fails in practice — not a diagram you copied once.

Test pyramid

Classic shape: many unit tests, fewer integration tests, few e2e tests. Unit tests run on every save or PR; e2e runs on merge to main or nightly because they are slow and can flake on infra. The pyramid keeps feedback fast while still proving critical paths end-to-end.

Testing trophy (integration-heavy)

For services with lots of I/O — HTTP APIs, databases, queues — teams often invest more in integration tests with real dependencies in containers. Unit tests still cover pure logic; e2e stays small. ML pipelines fit here too: test data loaders and eval harness against fixture files, not only mocked tensors.

Shift-left

Shift-left means finding defects earlier: lint and unit tests on the developer machine, then the same suite in CI on every pull request. Fail fast on the cheapest stage — do not discover a broken import only after a 40-minute deploy. Pre-commit hooks help for formatting; keep heavy integration in CI with cached deps.

What to add first on a new feature
  1. Happy path for the new behavior (unit or API test).
  2. One or two error cases (invalid input, auth failure, empty result).
  3. Regression test if you fixed a production bug.
  4. Integration test if the feature touches persistence or a third party.
  5. Smoke or e2e only if the feature is a full user journey or deploy-critical.
TDD vs test-after

Test-driven development (TDD) writes a failing test, then minimal code to pass, then refactor — great for crisp APIs and parsers. Test-after is fine when exploring; add tests before merge so main stays protected. Neither replaces design review or production monitoring (observability).

Other techniques (when they help)
  • Parametrized tests — same logic, many input rows (edge cases without copy-paste).
  • Property-based testing — generate random inputs; assert invariants (e.g. sort is ordered, decode(encode(x)) == x).
  • Snapshot tests — compare output to a stored file; good for serializers and stable reports; risky for LLM text unless you pin seeds and scope tightly.
  • Mutation testing — deliberately break code to see if tests catch it; advanced, usually later.
CI layering (pointer)

Typical PR job: lint, typecheck, fast unit tests. Optional parallel job: integration with service containers. Nightly or pre-release: e2e, load smoke, full ML eval (MLOps pipelines). Pipeline mechanics live on CI/CD.

Chooser

Library or pure ML math → pyramid-heavy, mostly unit. BFF or microservice → trophy: integration + contract tests, few e2e. Agent or RAG product → unit for tools and schema, integration with mocked LLM, golden eval for quality (ML testing).
