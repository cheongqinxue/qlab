Testing — performance & load

Objectives

Performance testing answers how fast and how much under controlled load. You set targets before the test (latency percentiles, throughput, error rate) and compare results to those targets. Load testing finds breaking points and queue buildup before a launch or traffic spike does it for you.

Terms
  • Latency — time one request takes (report p50, p95, p99, not only average).
  • Throughput — requests or tokens per second the system sustains.
  • Concurrency — how many in-flight requests (users or workers).
  • Soak test — moderate load for hours; catches memory leaks and connection pool exhaustion.
  • Spike test — sudden jump in traffic; tests autoscaling and backoff.
  • Stress test — increase load until errors rise; find the knee of the curve.
Performance vs load vs capacity
Kind Question When
Micro-benchmark Is this function hot? During optimization; not a substitute for system tests
Load test Do we meet SLO at expected RPS? Pre-release, after infra change
Capacity plan How many replicas for peak? Quarterly or before major event
ML and LLM serving specifics
  • Measure time-to-first-token (TTFT) and tokens/sec separately for streaming APIs.
  • Warmup — first request compiles CUDA graphs or loads weights; exclude warmup from SLO stats or report cold vs warm.
  • Batching changes latency–throughput tradeoff; load test with realistic batching settings from production.
  • GPU memory caps max batch size; stress until OOM or queue timeout to know headroom.
Tools (common choices)
Tool Notes

Example — k6 threshold smoke 
import http from "k6/http";
import { check, sleep } from "k6";

export const options = {
  vus: 10,
  duration: "30s",
  thresholds: {
    http_req_failed: ["rate<0.01"],
    http_req_duration: ["p(95)<500"],
  },
};

export default function () {
  const res = http.post(
    `${__ENV.BASE_URL}/v1/chat`,
    JSON.stringify({ message: "ping" }),
    { headers: { "Content-Type": "application/json" } }
  );
  check(res, { "status 200": (r) => r.status === 200 });
  sleep(1);
}

Run against staging with production-like hardware when possible; a laptop hitting localhost is only a smoke signal.

Example — Locust user flow 
from locust import HttpUser, task, between

class ApiUser(HttpUser):
    wait_time = between(0.5, 2.0)

    @task(3)
    def predict(self) -> None:
        self.client.post("/predict", json={"features": [1.0, 2.0, 3.0]})

    @task(1)
    def health(self) -> None:
        self.client.get("/health")

Weight tasks to match real traffic mix; a load test that only hits /health lies about capacity.

Environment and fairness
  • Load generators must not become the bottleneck — scale k6/Locust workers or run from the same region as the service.
  • Use dedicated staging; never unplanned load against prod without a game day process.
  • Fix dataset size and auth tokens; realistic payloads beat tiny JSON ping bodies for ML APIs.
  • Watch server metrics during the run — CPU, GPU util, queue depth, 5xx rate (observability).
CI placement

Full load tests rarely belong on every PR — they are noisy and expensive. Use a short k6 smoke (few VUs, 30s) on merge to main, or nightly full runs with trend charts. Pair with unit-level timeouts on critical paths so obvious regressions still fail fast in PR CI.

Chooser

Optimizing one kernel → micro-benchmark + profiler, then confirm with end-to-end load. Launching API → load test at 2× expected peak with p95 SLO. Long-running workers → soak test overnight. Black Friday / model viral moment → spike + autoscale validation.
