LLM autoscaling

What is autoscaling?

Autoscaling automatically adds or removes compute when demand changes, so inference keeps meeting service level objectives (SLOs) without manual kubectl scale every time traffic moves. For self-hosted LLMs that means more (or fewer) vLLM pods, optional Ray Serve replicas, graphics processing unit (GPU) nodes in the cluster, and separate scaling for the agent tier.

Goal: hit latency targets (especially time to first token (TTFT)) and availability while avoiding idle GPUs. Demand swings with users, campaigns, and time of day — baseline capacity alone is either too small (queues) or too large (cost).

Load balancing versus autoscaling

They solve different problems and are used together.

  • Load balancing spreads requests across existing backends — Kubernetes Service / ingress (nginx, Envoy, cloud load balancer), or Ray Serve’s router. Health checks steer traffic away from bad pods.
  • Autoscaling changes how many backends exist — replica count on the vLLM Deployment, Ray Serve min_replicas / max_replicas, or GPU nodes when new pods cannot schedule.

More replicas help only if the load balancer can reach them; autoscaling helps only if metrics say you need another copy of the model loaded on GPU.

How autoscaling works (in our stack)
Typical flow
  1. Baseline deployment — infrastructure as code (Helm, Kustomize, Terraform): vLLM container, pinned model, nvidia.com/gpu request, probes, --max-num-seqs / --max-model-len from VRAM sizing.
  2. Policy & thresholds — when a metric crosses a target for long enough, increase replicas; after a cooldown, decrease. Tooling: Kubernetes Event-driven Autoscaling (KEDA) or Horizontal Pod Autoscaler (HPA) with Prometheus metrics; or Ray Serve autoscaling_config.
  3. Placement — scheduler binds pods to GPU nodes. If none free, pods stay Pending; Cluster Autoscaler (CA) (GKE/EKS/AKS node pool autoscaler) adds machines — configured separately from pod autoscalers.
  4. Admission — if scale-out is slow (cold start: pull image + load weights), the backend-for-frontend (BFF) or gateway returns HTTP 429 Too Many Requests instead of unbounded queue — not autoscaling, but part of the same SLO story.
Autoscaling groups (min / max)
  • vLLM Deployment — minReplicas / maxReplicas (KEDA ScaledObject or HPA).
  • Ray Serve LLM deployment — min_replicas, max_replicas, target_ongoing_requests.
  • KubeRay worker group (optional) — minReplicas / maxReplicas on RayCluster worker pods when Ray needs more GPU slots.
  • GPU node pool — min / max node count and cloud GPU quota; cap Serve max_replicas to what you can schedule.
  • Agent Deployment — central processing unit (CPU) pool, its own HPA/KEDA; demand correlates with LLM calls but replica counts differ.
Mixed workload shapes (like “instance types”)
  • GPU inference — vLLM (memory-bound key-value (KV) cache + batching); scale on waiting queue, not GPU %.
  • CPU encoders — toxicity / decision transformers on Ray Serve or separate Deployments; scale on in-flight or R × LLM replicas from load tests.
  • Agent orchestration — LangGraph/FastAPI; scale on requests per second (RPS) / CPU; may colocate tiny models in-process.
Types of scaling
Horizontal versus vertical
  • Horizontal (scale out / in) — add vLLM pods or Ray Serve replicas behind the load balancer. Each replica is usually a full model copy (or one tensor parallel (TP) group = N GPUs in one pod).
  • Vertical (scale up / down) — bigger GPU SKU, TP across devices, or tune --max-num-seqs / quant / FP8 KV inside one replica. Kubernetes does not auto-resize GPU per pod; you change the Deployment template or node pool SKU.

LLM production autoscaling is mostly horizontal replicas + horizontal GPU nodes; vertical changes are deploy-time capacity planning.

Autoscaling policy modes
Dynamic scaling (reactive)

Adjust capacity when metrics say load is high or low — the default for burst traffic.

  • Signal: vLLM num_requests_waiting (best leading indicator); or in-flight per pod vs target (Ray target_ongoing_requests). Use TTFT 95th percentile (p95) to validate SLOs, not as the only trigger.
  • Tooling: KEDA Prometheus trigger on waiting sum; HPA with Prometheus adapter; Ray Serve upscale_delay_s / downscale_delay_s (long downscale for LLM cold start).
  • Anti-pattern: HPA on GPU or CPU utilization alone — queue builds while utilization looks fine.
Scheduled scaling

Raise or lower capacity on a calendar when demand is predictable.

  • CronJob or GitOps schedule patches minReplicas on vLLM or GPU node pool min before daily peaks.
  • Ray: raise min_replicas before a known event (same idea as pre-warm in runbooks).
Predictive scaling

Use history or live leading indicators to move the floor before queues form.

  • Hour-of-week baselines → higher minReplicas or warm GPU nodes.
  • Active users / sessions in Prometheus → KEDA scales min or gives early upscale (multiply by measured LLM-call rate per user).
  • Keep dynamic scaling on waiting/in-flight for spikes the forecast missed.

Agent, LLM, and encoders together

Traffic: users → agent Deployment → HTTP → vLLM (± Ray Serve encoders). Agent scale leads GPU demand but is not 1:1 — tool-only turns and shared LLM pools break simple coupling.

  • Scale GPU pods on waiting at vLLM; scale agent on RPS / CPU.
  • Encoders: same request rate as LLM if one call per turn — higher target_ongoing_requests per CPU pod or fixed ratio to LLM replicas.
Benefits (when policies match LLM reality)
  • Consistent performance — fewer surprise TTFT cliffs if waiting-queue triggers and min replicas match cold-start time.
  • Cost — scale in during troughs (with long downscale delay); avoid permanent overprovisioned GPU fleets.
  • Less manual ops — policies replace heroic kubectl scale; runbooks for when autoscaler hits quota or pending storms.
  • User experience — bounded wait (429) beats minute-long silent queues when GPUs cannot appear instantly.

Production checklist
  1. Load-test: waiting threshold, cold-start time, pick min/max replicas and pool max.
  2. Dashboard: waiting, in-flight, replicas ready vs desired, Pending pods, TTFT p95.
  3. Align cloud GPU quota with max_replicas × GPUs per pod.
  4. Failure modes: pending replica storm, out-of-memory (OOM), retries — runbooks.
  5. Economics: hosting cost context.
