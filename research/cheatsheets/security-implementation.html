Security — implement & deploy

What you need to understand (no jargon wall)
Four ideas that drive every decision
  1. The browser is not yours. Anything in JavaScript can be edited. Hiding buttons is not security. The API must enforce rules.
  2. Login ≠ permission. Knowing who someone is (AuthN) does not tell you if they may open this record (AuthZ). You need both, on every sensitive route.
  3. Credentials are bearer secrets. Whoever holds the session cookie or access token is treated as that user until it expires or is revoked.
  4. IDs in URLs are not proof. GET /invoices/42 must load invoice 42 and check “does this logged-in user own or admin invoice 42?” — not “are they logged in?”

Trust boundary: Internet → your edge (TLS) → your app (AuthN+AuthZ) → database (optional row locks).

Vocabulary (spelled out once)
  • IdP (identity provider) — runs login: Clerk, Auth0, Cognito, Firebase Auth, Google
  • OIDC (OpenID Connect) — “Sign in with X” standard; yields an ID token about the user
  • JWT (JSON Web Token) — signed JSON; backend verifies signature before trusting sub (user id)
  • AuthN / AuthZ — authentication (who) vs authorization (what they may do on which row)
  • RBAC (role-based access control) — admin / member mapped to allowed actions
  • RLS (row-level security) — Postgres filters rows by policy (e.g. only where user_id = me)
  • Tenant — one customer org in B2B software; rows tagged organization_id
Permission models vs products

RBAC/ABAC/ReBAC are ways to think about rules. Software that implements them includes Casbin, Oso, OPA, SpiceDB, Auth0 FGA, and Postgres RLS. The IdP gives coarse roles in the token; per-row access is usually your app or RLS.

What you should not build yourself (first ship)
  • Password hashing schemes, MFA crypto, OAuth server from scratch
  • Custom session crypto — use framework + IdP patterns
  • “Security by obscurity” API keys in frontend bundles
  • Buy/host: managed auth unless compliance forces self-host (Keycloak on VPC)
Pick your path — then implement that path
Path A — Consumer web/mobile app

Users sign up, log in, use your product.

After login at Google/Firebase/etc., the client keeps a token (often a JWT). The client sends that token on each API request; the backend verifies it with the same provider (Firebase Admin, Google JWKS, Auth0, …). That verification is AuthN. AuthZ is your code: roles plus matching user_id on the row.

  • Use managed auth — do not build OAuth/password crypto yourself
  • Prefer HttpOnly session cookie or backend-for-frontend (BFF) over JWT in localStorage
  • AuthZ start — user_id column + check in handler; add Postgres RLS when you want a DB safety net
Path B — B2B SaaS (teams / companies)
  • Every row has organization_id (tenant); JWT carries org_id from IdP or your DB
  • RBAC: org_admin vs member; invite flows
  • Enterprise: SAML/OIDC SSO to customer IdP (Okta, Entra ID)
  • Add Postgres RLS when one bug could cross tenants
Path C — API / scripts / backend only
  • API keys for servers you control — rotate, scope, rate-limit, never in browser
  • OAuth client credentials service-to-service where IdP supports it
  • Cloud: workload identity (IAM role → short-lived token), not static keys on disk
Reference deploy shape (typical SaaS)
Phased implementation — do in order
Phase 0 — before users (1–2 days)
  • HTTPS on prod (Let’s Encrypt or cloud LB certificate)
  • .env + .env-template; secrets in gitignored env or cloud secret manager
  • All mutating routes behind AuthN — no “we’ll add later” on DELETE/PUT
  • Default deny: new endpoints return 401 until wired
  • Separate prod vs staging IdP apps and secrets
Phase 1 — first real users
  • Managed IdP wired; email verification or SSO as needed
  • Object-level checks: load resource → compare owner/tenant → then return data
  • RBAC table or claims: role checked on admin routes (BFLA)
  • Rate limit login and password reset at edge
  • Structured audit log: user id, action, resource id, timestamp (no tokens)
Phase 2 — scale & enterprise
  • MFA enforced for admins; SSO for enterprise tenants
  • Refresh token rotation; session revoke on password change
  • Postgres RLS or policy engine (OPA/Cedar/SpiceDB) if sharing rules get messy
  • Pen test or automated DAST on staging; fix BOLA findings first
What your application code must do (every stack) 
1. Middleware: parse cookie OR Authorization Bearer
2. Validate with IdP (JWKS) or session store → set request.user { id, roles, tenant_id }
3. Handler: resource = db.get(id); if resource.tenant != user.tenant: return 403
4. Handler: if action needs role and role not in user.roles: return 403
5. Proceed with business logic

Write automated tests that user A cannot read user B’s id — expect 403/404, not 200.

Managed auth — what you configure
  • Redirect URIs — exact allowlist (prod + staging URLs); typo = auth bypass confusion
  • Client secret — server-side only; SPAs use PKCE without secret
  • JWT audience — API only accepts tokens meant for your API (aud)
  • Custom claims — tenant_id, role via rules or post-login hook
  • Webhooks — verify signature when IdP sends user.updated / delete
Deploy checklist (prod cutover)
  • TLS valid; HSTS optional; no HTTP login
  • CORS: explicit origin list if browser sends cookies — never * + credentials
  • Cookie flags: Secure, HttpOnly, SameSite=Lax (or Strict)
  • Admin UI on separate path or subdomain; stricter MFA policy
  • Backups encrypted; DB not public IP
  • Incident: document how to revoke all sessions (IdP dashboard or key rotation)
Gotchas — read before launch
Tokens & sessions
  • JWT in localStorage — any XSS steals account; prefer HttpOnly cookie or BFF
  • Long-lived access JWT — stolen token works for days; use short access + refresh
  • No revocation story — know how to force logout (session version, blocklist, IdP revoke)
  • Accept alg=none or skip signature verify — always verify with IdP JWKS
  • Trust client “userId” field in JSON body — use identity from verified token only
Authorization bugs (most common breaches)
  • BOLA/IDOR — increment id in API; fix with server-side ownership check every time
  • AuthZ only in UI — attacker calls API directly
  • Admin routes unguarded — /admin/* missing role middleware
  • Mass assignment — user submits {"role":"admin"} on profile update
  • 404 vs 403 — leaking existence can matter; pick consistent policy
Multi-tenant
  • Tenant id from query string — must match token claim, not user input alone
  • Forgot tenant in worker/cron — job processes all tenants’ data
  • Cache keys without tenant — user A sees user B’s cached fragment
  • Support “impersonation” without audit trail — log every impersonation session
OAuth & login flows
  • Open redirect — validate returnUrl against allowlist
  • Redirect URI mismatch — attacker registers lookalike if IdP misconfigured
  • Implicit flow in SPA — deprecated; use authorization code + PKCE
  • CSRF on OAuth state — use state param and verify on callback
API keys & ops
  • Key in frontend / mobile app — extractable; use user login instead
  • Same key prod and dev — leak in ticket exposes prod
  • Logs — Authorization header, query tokens, password reset links logged by default in some proxies
  • Webhooks — verify HMAC signature; no auth “because it’s internal IP”
  • GraphQL — one endpoint still needs per-field or per-resolver AuthZ
When things go wrong
  • Rotate IdP client secret / API keys if leaked; invalidate sessions
  • Force global password reset only if password store compromised
  • Post-mortem: was failure AuthN, AuthZ, or missing tenant filter?
Minimum test cases before you trust it
  • Anonymous cannot call protected route (401)
  • User A cannot read/update User B’s resource by id (403/404)
  • Member cannot call admin endpoint (403)
  • User in Org 1 cannot access Org 2 data when swapping org header
  • Expired/tampered token rejected (401)
