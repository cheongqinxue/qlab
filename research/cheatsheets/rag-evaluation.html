RAG evaluation

Evaluate in three layers

Retrieval asks whether the right evidence appears in the candidate list (recall@k, nDCG, MRR) — independent of the LLM. Generation asks whether the answer is supported by the evidence actually placed in the prompt (faithfulness, citation precision) and optionally whether it matches human gold text (exact match, F1) or real-world truth (correctness). End-to-end runs the full pipeline on realistic queries and scores task success, user satisfaction, or business outcomes. A high recall@5 with low faithfulness means fix ranking or generation; high faithfulness with angry users means fix sources or correctness — see hallucination diagnosis.

Golden sets and qrels
Building labeled data

A golden query set is a fixed list of questions with known expectations. Qrels (query relevance judgments) map each query to relevant chunk or document ids — binary or graded. Sources: human annotators on real support questions; expert-written FAQ pairs; or synthetic questions generated from held-out chunks with the positive id known by construction (embedder eval). Hold out entire documents from any training or tuning that touches retrieval. Refresh the set when the corpus or product domain shifts; version the file in git like a model artifact.

Slices and regression gates

Report metrics on the full set and on slices: locale, product line, queries with order IDs or error codes, long vs short questions, and permission-sensitive queries. CI should fail a release when any critical slice drops more than a tolerance on recall@k or faithfulness compared to the previous index or prompt version. Keep a small “must never break” set (50–200 queries) for every deploy of embed model, chunk policy, reranker, or LLM prompt.

Retrieval metrics (offline)
What to compute and when

Recall@k measures whether any gold relevant chunk appears in the top k returned — use the same k as production (often 5–10 after rerank, 50–100 before rerank). Recall@1 vs recall@5 gap diagnoses wrong ranking when gold is in the list. Precision@k matters when context window is tight or reranker cost is high. MRR suits one gold chunk per query; nDCG suits graded relevance. Hit rate@k is the per-query “any relevant in top k” rate — easy for dashboards. Formulas and definitions live on metrics. ANN tuning uses the same qrels — ANN sheet.

Retriever-only vs full pipeline

Run retrieval metrics with the production hybrid + fusion + rerank stack but without calling the LLM — fast iteration on chunking and embed changes. Optionally report an oracle reader score: give the gold chunk to the LLM and measure answer quality — upper bound showing how much retrieval alone limits end-to-end quality.

Generation and grounding metrics
Faithfulness, correctness, citations

Faithfulness (groundedness): each atomic claim in the answer is entailed by the retrieved context shown to the model — typically NLI cross-encoder, RAGAS-style decompose-then-verify, or calibrated LLM-as-judge. Answer correctness: matches authoritative gold (human label or policy doc), independent of whether the model quoted the right chunk. Citation precision: cited chunk ids exist and contain the cited span; citation recall: claims that need support have a citation. High faithfulness with low correctness means stale or wrong KB — not a generation-only fix.

Abstention and empty retrieval

Track the rate at which retrieval scores fall below threshold and the model should refuse. Score proper abstention on queries with no relevant docs in the index (should not invent). Score false refusal when gold exists but the pipeline said “I don’t know.” Both belong in the golden set explicitly.

LLM-as-judge and automation
When judges help and when they lie (full guide: LLM as a judge)

LLM judges scale cheaply for faithfulness and helpfulness on hundreds of pairs. Calibrate against a human-labeled subset (50+ per domain); report judge–human agreement. Judges favor verbose, confident answers and can share the same biases as the generator — do not use them as the only gate for regulated content. Prefer deterministic checks where possible: citation id in allowlist, numeric answers match tool JSON, regex on required policy phrases. Tools such as RAGAS, ARES, and DeepEval implement common patterns; treat them as starting pipelines, not black-box pass/fail without domain calibration.

Release workflow
Offline gates before production

Typical order for an index or prompt change: (1) retrieval recall@k / nDCG on golden qrels; (2) faithfulness and citation metrics on full pipeline with frozen LLM; (3) end-to-end answer correctness on human gold; (4) security slice (ACL: forbidden cross-tenant retrieval in tests). Block merge if any gate regresses beyond tolerance. Store retrieved chunk ids in eval logs so failures are debuggable without re-running blind — aligns with diagnosis workflow.

Online and A/B evaluation

Offline sets lag real query drift. In production, sample traces for human review or LLM judge; track escalation rate, thumbs down, time to resolution, and task-specific KPIs (deflection, CSAT). Run shadow retrieval (new index returns candidates but does not affect answers) before cutover. A/B new reranker or model on a fraction of traffic with pre-registered primary metric and guardrails (latency, abstention rate). Log faithfulness on a small daily sample even when offline CI passed.

Common mistakes

Optimizing BLEU/ROUGE on paraphrased answers while users need factual grounding. Reporting recall@k on k much larger than production context. Leaking golden queries into embed fine-tuning. Single aggregate faithfulness score hiding slice collapse (e.g. ID-heavy queries). Shipping when only the LLM changed without re-running faithfulness on the same retrieved contexts.

Mitigation after eval fails

Retrieval failures → chunking, fusion, embedders. Faithfulness failures → grounding mitigations. Wrong facts with high faithfulness → ingest freshness and source of truth.
