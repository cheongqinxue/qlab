Transformers — serving & hosting

What this sheet is (and is not)

Serving / hosting is everything that turns a checkpoint into a stable inference service: load weights, batch requests, stream tokens, expose an API, scale replicas, and match hardware to latency and cost. This page covers runtimes, deployment shapes, and ops levers — not model architecture (core) and not kernel-level KV math alone (efficiency).

Deployment shapes
Self-host on your GPUs

You operate machines (or K8s), pick a serving engine, pin CUDA/driver, and own uptime. Best when data must stay in VPC, you need custom quant (GPTQ/AWQ/FP8), or unit economics beat API pricing at steady load.

Managed model APIs

Vendor hosts weights and GPUs; you call HTTPS (OpenAI-style or cloud-native). Best for fast start, bursty traffic, and when ops headcount is limited — watch data residency, logging, and $/1M tokens.

Edge & local

llama.cpp, Ollama, MLX on laptop or on-prem CPU/GPU — low latency, offline, dev demos. Different scale ceiling than datacenter vLLM; often GGUF/INT quants.

Hybrid

App in your cloud; inference via private link to Bedrock/Vertex/Azure OpenAI, or burst overflow from self-host to API. LiteLLM / gateways unify routes (reliability).

Architecture levers (beyond “pick vLLM”)
Throughput vs latency
  • Continuous batching — merge decode steps across users; boosts GPU util, adds tail latency jitter.
  • Static batching — simpler; fine for offline batch inference.
  • Max batch tokens / max seqs — tune to avoid OOM; document in runbooks.
Scale-out
  • Tensor parallel (TP) — one model sharded across GPUs in a replica.
  • Pipeline parallel (PP) — layers on different devices; less common at small scale.
  • Data parallel replicas — multiple full copies behind a load balancer.
  • Expert parallel (EP) — MoE-only; must match training shard semantics (efficiency).
Disaggregated prefill / decode

Split prompt-heavy prefill and token-by-token decode onto different pools (research + early prod on large models). Helps when prefill compute-bound and decode memory-bound; adds network hop and scheduler complexity.

Multi-LoRA & adapters

One base weights copy, many LoRA adapters swapped or batched (PEFT). vLLM/SGLang multi-LoRA reduces RAM vs full fine-tunes; define max adapters and eviction policy.

API surface & clients
  • OpenAI-compatible — /v1/chat/completions, streaming SSE; de facto for apps and LangChain-class SDKs.
  • Embeddings & rerankers — often separate smaller services (TEI, Infinity, custom FastAPI + sentence-transformers).
  • Speech / vision — separate pipelines (Whisper serve, vLLM multimodal) — not every LLM engine hosts all modalities.
  • gRPC / Triton — lower latency internal east-west; common with TRT-LLM in NVIDIA stacks.
Hosting ops checklist
Lifecycle
  • Model registry (HF revision, quant recipe hash, license).
  • Health: warm model loaded, generate 1 token, latency SLO.
  • Rollout: canary replica, compare error rate and tokens/sec.
  • Cold start: serverless and large models — preload or keep min replicas > 0.
Capacity planning
  • VRAM = weights + KV × concurrent seqs (KV quant).
  • Decode QPS often limited by memory bandwidth, not FLOPs.
  • Reserve headroom for long-context spikes and agent multi-turn.
Chooser
  • Prototype / laptop → Ollama or llama.cpp; same prompts later against vLLM in staging.
  • Prod GPU you operate → vLLM or SGLang; TP for 70B+; gateway for fallbacks.
  • Max NVIDIA perf, fixed model → TensorRT-LLM build pipeline.
  • No GPU ops team → managed API or Inference Endpoints; log residency requirements first.
  • RAG product → LLM serve + dedicated embedding/rerank service; do not overload one process if CPU embed blocks GPU decode.
