Transformers — serving & hosting

What this sheet is (and is not)

Serving / hosting is everything that turns a checkpoint into a stable inference service: load weights, batch requests, stream tokens, expose an API, scale replicas, and match hardware to latency and cost. This page covers runtimes, deployment shapes, and ops levers — not model architecture (core) and not kernel-level KV math alone (efficiency).

Deployment shapes
Self-host on your GPUs

You operate machines (or K8s), pick a serving engine, pin CUDA/driver, and own uptime. Best when data must stay in VPC, you need custom quant (GPTQ/AWQ/FP8), or unit economics beat API pricing at steady load.

Managed model APIs

Vendor hosts weights and GPUs; you call HTTPS (OpenAI-style or cloud-native). Best for fast start, bursty traffic, and when ops headcount is limited — watch data residency, logging, and $/1M tokens.

Edge & local

llama.cpp, Ollama, MLX on laptop or on-prem CPU/GPU — low latency, offline, dev demos. Different scale ceiling than datacenter vLLM; often GGUF/INT quants.

Hybrid

App in your cloud; inference via private link to Bedrock/Vertex/Azure OpenAI, or burst overflow from self-host to API. LiteLLM / gateways unify routes (reliability).

Architecture levers (beyond “pick vLLM”)
Throughput vs latency
  • Continuous batching — merge decode steps across users; boosts GPU util, adds tail latency jitter.
  • Static batching — simpler; fine for offline batch inference.
  • Max batch tokens / max seqs — tune to avoid OOM; document in runbooks.
Scale-out
  • Tensor parallel (TP) — one model sharded across GPUs in a replica.
  • Pipeline parallel (PP) — layers on different devices; less common at small scale.
  • Data parallel replicas — multiple full copies behind a load balancer.
  • Expert parallel (EP) — MoE-only; must match training shard semantics (efficiency).
Disaggregated prefill / decode

Split prompt-heavy prefill and token-by-token decode onto different pools (research + early prod on large models). Helps when prefill compute-bound and decode memory-bound; adds network hop and scheduler complexity.

Multi-LoRA & adapters

One base weights copy, many LoRA adapters swapped or batched (PEFT). vLLM/SGLang multi-LoRA reduces RAM vs full fine-tunes; define max adapters and eviction policy.

API surface & clients
  • OpenAI-compatible — /v1/chat/completions, streaming SSE; de facto for apps and LangChain-class SDKs.
  • Embeddings & rerankers — often separate smaller services (TEI, Infinity, custom FastAPI + sentence-transformers).
  • Speech / vision — separate pipelines (Whisper serve, vLLM multimodal) — not every LLM engine hosts all modalities.
  • gRPC / Triton — lower latency internal east-west; common with TRT-LLM in NVIDIA stacks.
VRAM sizing for inference

Total GPU memory for one replica is approximately weight footprint + KV cache for all active sequences + engine overhead. Weights are fixed at load time; KV grows with each token stored for each concurrent request. Decode throughput is often limited by memory bandwidth reading KV, not by FLOPs (efficiency). The formulas below ignore tensor-parallel sharding (divide per-GPU totals by TP size) and treat vision or audio towers as extra weight bytes on multimodal checkpoints.

Weights — express model size as P_B = parameter count in billions (Llama 3.1 8B → P_B = 8). Rule-of-thumb GiB:

Weight GiB ≈ P_B × 2

BF16/FP16 — 16 bits per param → ~2 GiB per billion parameters (8B → ~16 GiB)

Weight GiB ≈ P_B × 0.5

ideal INT4 — 4 bits per param (8B → ~4 GiB)

Weight GiB ≈ P_B × 0.55

shipped AWQ/GPTQ — ~4.5 bits/param effective with scales/packing (8B → ~4.4 GiB); prefer HF Disk size when listed

Precise: weight bytes = N_params × weight_bits_per_param ÷ 8, then Weight GiB = weight bytes ÷ 230 (one gibibyte = 230 bytes, not 109). The P_B shortcuts treat “8B” as 8×109 and are close enough for capacity planning; use the exact line when you are within a few GiB of a GPU limit.

MoE checkpoints still load all expert tensors in most vLLM/SGLang layouts unless you use expert-parallel or offloading — size from the HF card, not active parameters only.

KV cache — one sequence, all layers:

KV bytes = 2 × num_layers × n_kv_heads × head_dim × seq_len × (kv_bits_per_element ÷ 8)
  • 2key tensor and value tensor
  • num_layerstransformer block count
  • n_kv_headsGQA key/value head count
  • head_dimdimension per KV head
  • seq_lentokens stored for that sequence
  • kv_bits_per_element16 for FP16/BF16 KV; 8 for FP8/INT8 KV where supported
Total KV bytes = KV bytes × concurrent_sequences

max-num-seqs (vLLM) or max-running-requests (SGLang)

Hybrid or linear-attention layers cache less; use the model card or treat KV as a lower fraction of the dense estimate.

vLLM — dtype, weight quant, KV quant

Set --max-num-seqs 10 and --max-model-len 8192 to align with the VRAM table. For offline AWQ/GPTQ checkpoints, omit --quantization: vLLM reads quantization_config in config.json and picks auto_awq / Marlin when eligible. Passing --quantization awq forces a legacy path and can fail on modern AutoAWQ repos — only use -q when docs require an override (e.g. explicit gptq vs marlin). 

# BF16/FP16 weights, full-precision KV
vllm serve meta-llama/Llama-3.1-8B-Instruct \
  --dtype bfloat16 \
  --max-model-len 8192 \
  --max-num-seqs 10 \
  --gpu-memory-utilization 0.90

# Pre-quantized AWQ (AutoAWQ on HF) — no --quantization flag
vllm serve hugging-quants/Meta-Llama-3.1-8B-Instruct-AWQ-INT4 \
  --dtype auto \
  --max-model-len 8192 \
  --max-num-seqs 10

# Same checkpoint + FP8 KV (CLI value is fp8; maps to fp8_e4m3 on supported GPUs)
vllm serve hugging-quants/Meta-Llama-3.1-8B-Instruct-AWQ-INT4 \
  --dtype auto \
  --kv-cache-dtype fp8 \
  --max-model-len 8192 \
  --max-num-seqs 10

FP8 KV and GPU generation: Ada Lovelace (L4, RTX 40xx) and Hopper (H100) are the straightforward targets for --kv-cache-dtype fp8. Ampere (A100, RTX 30xx) has no native FP8 tensor cores; FP8 KV may still work when the attention backend stores FP8 but computes in BF16/FP16 (e.g. FlashInfer on A100 in recent vLLM builds). If init fails with an architecture or Triton fp8e4nv error, stay on BF16/FP16 KV, try VLLM_ATTENTION_BACKEND=FLASHINFER, or pin a vLLM version whose release notes cover SM80 FP8 KV — behavior moves quickly. Optional: --calculate-kv-scales or calibrated scales on long context; fp8_e5m2 remains an explicit alternative where supported.

SGLang — dtype, weight quant, KV quant

Same rule for offline-quantized weights: do not pass --quantization awq (that is for on-the-fly quant). SGLang parses the method from the HF config.json. For FP8 KV, SGLang’s CLI uses explicit fp8_e4m3 or fp8_e5m2 (there is no short fp8 alias like vLLM). Supply --quantization-param-path when FP8 KV scales are not embedded in the checkpoint. 

# BF16 weights, full-precision KV
python3 -m sglang.launch_server \
  --model-path meta-llama/Llama-3.1-8B-Instruct \
  --dtype bfloat16 \
  --context-length 8192 \
  --max-running-requests 10

# Pre-quantized AWQ — no --quantization flag
python3 -m sglang.launch_server \
  --model-path hugging-quants/Meta-Llama-3.1-8B-Instruct-AWQ-INT4 \
  --dtype auto \
  --context-length 8192 \
  --max-running-requests 10

# AWQ + FP8 KV (SGLang: fp8_e4m3 recommended for accuracy in docs)
python3 -m sglang.launch_server \
  --model-path hugging-quants/Meta-Llama-3.1-8B-Instruct-AWQ-INT4 \
  --dtype auto \
  --kv-cache-dtype fp8_e4m3 \
  --context-length 8192 \
  --max-running-requests 10

Confirm the chosen attention backend supports quantized KV; otherwise dequant paths can erase throughput gains. NVFP4 / block FP4 KV dtypes target Blackwell-class GPUs and ModelOpt checkpoints.

GCP GPU ladder for LLM inference (us-central1) — snapshot November 2026

Google’s first-party inference path is no longer “cheap T4 → expensive A100 only.” For self-host sizing we walk SKUs in VRAM order and pick the smallest machine that fits the high end of your quant-weight + KV range at ~90% memory utilization. Legacy N1 + T4 (~$0.35/h GPU, 16 GB) remains on the price list but is omitted here: 16 GB is too tight for typical agent KV loads, Turing lacks modern FP8 serve paths, and Google lists T4 end of support August 1, 2027 ([GPU machine types](https://cloud.google.com/compute/docs/gpus)).

Hosting ops checklist
Lifecycle
  • Model registry (HF revision, quant recipe hash, license).
  • Health: warm model loaded, generate 1 token, latency SLO.
  • Rollout: canary replica, compare error rate and tokens/sec.
  • Cold start: serverless and large models — preload or keep min replicas > 0.
Capacity planning
  • VRAM = weights + KV × concurrent seqs — walk through Llama 3.1 8B example and KV quant.
  • GCP SKU ladder (dated) → GCP GPU ladder; per-model table → LLM comparison — GCP self-host.
  • Decode QPS often limited by memory bandwidth, not FLOPs.
  • Reserve headroom for long-context spikes and agent multi-turn; load-test at product max context.
Chooser
  • Prototype / laptop → Ollama or llama.cpp; same prompts later against vLLM in staging.
  • Prod GPU you operate → vLLM or SGLang; TP for 70B+; gateway for fallbacks.
  • Max NVIDIA perf, fixed model → TensorRT-LLM build pipeline.
  • No GPU ops team → managed API or Inference Endpoints; log residency requirements first.
  • RAG product → LLM serve + dedicated embedding/rerank service; do not overload one process if CPU embed blocks GPU decode.
