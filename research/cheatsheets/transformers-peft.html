Transformers — PEFT & adapters

When to use PEFT
  • Many tasks on one base; limited GPU; cannot store full fine-tunes
  • Risk: underfitting (rank too low) or forgetting (rank too high, too many steps)
  • Stack adapters per tenant/task; swap at serve time
Adapter modules (Houlsby)
  • Bottleneck MLP after attention and/or FFN sublayer
  • Train adapter weights only; base frozen
  • Down-proj → nonlinearity → up-proj; small hidden width
LoRA
$$W' = W + BA,\quad B \in \mathbb{R}^{d \times r},\; A \in \mathbb{R}^{r \times k},\; r \ll d$$
  • Inject on $W_Q,W_K,W_V,W_O$ and/or FFN matrices
  • Merge $BA$ into $W$ at inference for zero extra latency
  • Default LLM fine-tune pattern (HF PEFT, many serving stacks)
Other PEFT methods
  • (IA)³ — learned scalars on activations
  • Prefix / prompt tuning — virtual tokens prepended; train embeddings only
  • BitFit — bias terms only (tiny, weak alone on hard tasks)
Generation conditioning (related)
  • ControlNet — trainable side network; frozen U-Net/DiT trunk
  • LoRA on diffusion — style/subject without full model copy
  • Not classic “adapter block” but same economic idea
Serving notes
  • Multiple LoRAs: compose or hot-swap per request (engine-dependent)
  • Version base + adapter artifacts together in registry
  • Eval on target task after merge — numerical drift is rare but possible
