DevOps — Kubernetes

What is Kubernetes?

Kubernetes (often abbreviated K8s) is a system that runs your container workloads across a pool of machines. You declare desired state (how many copies of an app, how much CPU or graphics processing unit (GPU) each needs); the control plane schedules pods onto nodes, restarts failed containers, and rolls out new versions.

You reach for K8s when you have multiple services, need high availability, or attach GPUs at scale — not for a first “hello API” unless the team already operates a cluster. Images and registries → containers.

Cluster anatomy
Control plane vs workers
  • Control plane — API server, scheduler, controllers; decides what should run where.
  • Node — a worker machine (virtual machine (VM) or bare metal) that runs your pods; cloud “node pools” are groups of similar nodes.
  • Pod — smallest deployable unit; one or more containers that share network and storage; usually one main container per pod for apps.
Deployment (replicated apps)

A Deployment owns a set of identical pods and keeps replicas at the number you set. Rolling updates replace pods gradually; scale up/down changes replica count. For inference, one vLLM pod often means one GPU and one model process per pod unless you use tensor parallel inside a multi-GPU pod.

Networking & load balancing
Service vs Ingress
  • Service — stable cluster-internal name and IP that load-balances across ready pods matching a label selector. Other pods (e.g. your agent) call http://vllm-service:8000.
  • Ingress — HTTP(S) entry from outside the cluster (often with a cloud load balancer in front). Terminates TLS and routes host/path to Services.

When people say “the load balancer sends traffic to the new vLLM instance,” in K8s that usually means: the new pod passes readiness, joins the Service endpoints, and the Service (or Ingress controller) starts including it in rotation.

Scheduling & resources
Requests, limits, and GPUs
  • requests — what the scheduler reserves when placing a pod (e.g. cpu: 2, memory: 8Gi).
  • limits — hard cap; exceed memory → out-of-memory (OOM) kill.
  • nvidia.com/gpu: 1 — request one GPU device; pod stays Pending if no node has a free GPU.
Pod phases you will see
  • Pending — not scheduled yet (no capacity, pulling image, waiting for GPU).
  • Running — scheduled; containers started.
  • CrashLoopBackOff — container exits repeatedly; check logs and probes.

kubectl describe pod <name> events often say Insufficient nvidia.com/gpu when the cluster is full.

Health checks
Liveness vs readiness
  • Liveness — “Is the process alive?” Fail → kubelet restarts the container.
  • Readiness — “Should this pod receive traffic?” Fail → removed from Service endpoints (no new requests) while still running.

For vLLM, readiness often waits until the model is loaded (and sometimes a cheap generate check). Traffic must not hit a pod until readiness passes — otherwise time to first token (TTFT) spikes on cold workers.

Autoscaling (two layers)
Pods vs nodes
Layer What changes Typical tooling
Pod count More/fewer replicas of your Deployment Horizontal Pod Autoscaler (HPA), Kubernetes Event-driven Autoscaling (KEDA)
Node count More/fewer machines when pods cannot schedule Cluster Autoscaler (CA) on cloud node pools

Scaling pods without free GPUs creates Pending pods — fix nodes or quota, not only “raise max replicas.” LLM metrics, Ray Serve, and policies → LLM autoscaling.

ML inference on Kubernetes
Common layout
  • Agent — CPU Deployment + Service; scales on requests per second (RPS) or CPU.
  • vLLM — GPU Deployment; image pins model + engine; probes on /health.
  • Ray on K8s (optional) — KubeRay RayCluster worker pods; Ray Serve sits on top — not required for plain vLLM.

Video RAM (VRAM) sizing and engine flags → serving. Incidents (pending replica storm, queues) → Ray + vLLM runbooks.

kubectl — what to run when
Command cheat sheet

kubectl is the CLI for the Kubernetes API. Add -n <namespace> when workloads are not in default (e.g. -n ray-system).

Command Shows Use when
kubectl get pods Phase, restarts, age, node (if scheduled) Quick scan — Pending vs CrashLoopBackOff
kubectl describe pod <name> Events, conditions, requests/limits, container last state Pod not ready — scheduling (Insufficient nvidia.com/gpu), image pull, probe failures, OOMKilled
kubectl logs <pod> Application stdout/stderr from the container Process errors after the pod is on a node — vLLM stack traces, config mistakes
kubectl logs <pod> --previous Logs from the last crashed container instance CrashLoopBackOff — current container may be empty
kubectl get deploy <name> READY vs desired replicas Autoscale or rollout — “want 6, have 1 ready”
kubectl get svc,ingress Cluster DNS names, ports, ingress hosts Traffic routing — agent cannot reach vLLM Service
kubectl get events --sort-by=.lastTimestamp Recent namespace events (sometimes duplicates describe) Cluster Autoscaler blocked, quota, failed mounts

describe vs logs: describe explains why Kubernetes has not marked the pod ready; logs explain why your app exited or misbehaved. Use both on GPU inference incidents.

Centralized logs and dashboards → observability. Pending replica storm runbook → Ray + vLLM.
