Metrics & evaluation

Training metric vs product metric

The training loss is what backprop minimizes — often cross-entropy (CE). It should correlate with what you care about, but rarely is the business goal. Pick one primary eval metric on a fixed held-out set and report it every run. Log extras for debugging, not as success unless they track the primary.

  • Same split rules as generalization — no train leakage into eval.
  • Generation tasks — automatic metrics are noisy; keep a small human or LLM-judge set for regressions.
Classical supervised (heads & tabular)
Classification
  • Accuracy — fine when classes are balanced; misleading when 99% negative.
  • Precision / recall / F1 — precision = of predicted positives, how many correct; recall = of true positives, how many found. F1 balances both.
  • ROC-AUC / PR-AUC — rank quality across thresholds; PR-AUC better on heavy imbalance.
  • Confusion matrix — which classes swap; read before tuning threshold.
High ROC-AUC, low precision at your production threshold

ROC-AUC summarizes ranking quality over all thresholds: positives tend to score higher than negatives. Precision at one threshold is what you live with in production: among rows you flagged positive, how many are truly positive? Both can be true at once — good separation in scores, bad precision because the operating point is wrong or the positive class is rare.

Reason 1 — threshold misfit. Validation picked a cutoff for high recall (or default 0.5) while the product needs high precision. Check: precision–recall curve on a held-out set; sweep threshold by cost matrix ($ of FP vs FN); report F1 only at the chosen operating point, not as a substitute for the sweep.

Reason 2 — class imbalance and base rate. When positives are rare, many false positives among predicted positives can drive precision down even with decent AUC. Check: class proportions in train vs production; PR-AUC (often more informative than ROC-AUC here); confusion matrix counts at the deployed threshold, not percentages alone.

Reason 3 — base rate / calibration shift. Scores rank well offline but the live population has fewer positives (or miscalibrated probabilities), so the same threshold fires too often. Check: reliability diagram / expected calibration error (ECE); compare predicted positive rate to observed positive rate on recent data.

Regression
  • MSE / RMSE — punishes large errors hard (squares).
  • MAE — robust to outliers.
  • R² — variance explained; can mislead if range shifts.
Calibration

When predicted probabilities matter (routing, risk), check if “80% confident” is right 80% of the time. ECE (expected calibration error) and reliability diagrams; temperature scaling on a val set fixes many models without retraining.

Language model pretraining
Perplexity & cross-entropy

Cross-entropy loss on next-token prediction is the standard train objective. Perplexity (PPL) is $\exp(\mathrm{CE})$ — “how surprised” the model is; lower is better. Comparable only with same tokenizer, vocab, and eval corpus.

  • Log train/loss and eval/loss or eval/perplexity on a fixed text slice.
  • PPL alone misses reasoning, safety, and tool use — always add task eval for LLMs you ship.
  • Bits per byte/character — sometimes used to compare across vocab sizes.
Entropy — three meanings
1. Uncertainty of a probability distribution

Shannon entropy measures how spread out a distribution is. For discrete classes or vocab tokens with probabilities $p_k$:

$$H(p) = -\sum_k p_k \log p_k$$

High $H$ → many outcomes similarly likely (uncertain). Low $H$ → one outcome dominates (confident/peaked). Maximum entropy for $K$ classes is $\log K$ (uniform $p_k = 1/K$).

2. Cross-entropy vs entropy (training loss)

Cross-entropy between true distribution $p$ and model $q$ is $-\sum_k p_k \log q_k$. When $p$ is a one-hot correct label, that is just $-\log q_y$ — the usual CE loss (loss functions).

Minimizing CE pushes $q$ toward $p$. It is not the same number as $H(q)$ unless you are explicitly logging softmax entropy. Perplexity is $\exp(\mathrm{CE})$ on the true token — average surprise per step, not $H(q)$.

3. Logit / softmax entropy (diagnostic)

Average $H(p)$ where $p$ is the model’s softmax over logits (next token or class). Use as a health metric, not the train loss.

  • Too low — model always nearly sure of one token; ties to logit_collapse (failure modes); try label smoothing or warmup.
  • Too high — near-uniform guesses; model not learning or temperature too hot at sample time.
  • Log train/logit_entropy or mean entropy over eval batches alongside CE/PPL.
Policy entropy (RL / PPO)

For a language policy, entropy is $H$ of the next-token distribution the policy samples from at each generated step (often averaged over the rollout). PPO adds an entropy bonus so the policy does not collapse to repeating one safe phrase while chasing reward.

  • Falling entropy during RL — normal early; if it crashes while reward flatlines, watch for mode collapse.
  • Rising entropy with rising reward — usually healthier exploration.
  • Pair with KL to reference — entropy alone does not tell you if you drifted from the SFT model.
Supervised fine-tuning (SFT)
What you optimize

Same token-level CE on demonstration conversations — often only on assistant tokens (mask user/system). Training loss going down means better fit to demos, not automatically better chat for users.

What you should eval
  • Held-out CE / PPL on a val instruction set (same mask rules as train).
  • Exact match (EM) — output equals reference string (QA, short answers).
  • Token F1 — overlap on answer span; common on extractive QA when wording varies.
  • Pass@k — for code: any of $k$ samples passes tests (HumanEval-style).
  • Task suites — MMLU slice, GSM8K, your domain golden prompts (fixed seed, fixed rubric).
Preference learning & RL (RLHF family)
Reward model (RM)

Trained to score (prompt, response) pairs — higher for human-preferred wins. Eval pairwise accuracy on a held-out preference set (did the RM rank the chosen response above the rejected one?). Watch length bias (RM loves verbose answers).

PPO (policy optimization)

Policy generates text; reward model (or rule) gives scalar reward. You log:

  • Mean reward — should trend up early; can overfit RM hacks later.
  • KL(policy ‖ reference) — drift from SFT checkpoint; too high = gibberish or policy collapse; too low = no gain. Target band is a hyperparameter.
  • Clip fraction — how often PPO clip binds; sanity on update size.
  • Policy entropy — see entropy section above; collapse → repetitive text.
  • Product eval — win rate vs baseline model on blind human or strong LLM judge; do not trust reward alone.

Loss shapes: PPO clipped surrogate, KL penalty.

DPO & offline preference

No separate RM at inference — train policy directly from chosen/rejected pairs. Monitor implicit reward margin on val pairs and win rate vs reference on generations. Still report KL to reference if logged.

GRPO & group-relative RL

Sample a group of completions per prompt; reward each; up-weight better-than-average trajectories (common in reasoning RL). Log group mean reward, std, and KL. Same warning: optimize a verifiable reward (math check, unit tests) when possible — not only a learned RM.

Generation quality (automatic)
  • BLEU / chrF — n-gram overlap to reference; brittle for paraphrases.
  • ROUGE — recall-oriented overlap; summarization legacy.
  • BERTScore / embedding sim — semantic similarity; better correlation sometimes, model-dependent.
  • LLM-as-judge — pairwise or scalar; useful for drafts; calibrate against human subset.

Information retrieval & ranking
Set-based (relevant or not)
  • Recall@k — fraction of all relevant docs that appear in top $k$. “Did we find it?”
  • Precision@k — fraction of top $k$ that are relevant. “Is the short list clean?”
  • Hit rate@k — per query, was at least one relevant doc in top $k$? (common in RAG product dashboards)
Rank-aware
  • MRR (mean reciprocal rank) — $1/r$ where $r$ is rank of first relevant doc; good when one gold doc per query.
  • MAP (mean average precision) — multiple relevant docs; rewards relevant items ranked high throughout the list.
  • nDCG — discounted gain by position; supports graded relevance (highly vs mildly relevant).

nDCG@k compares ranked lists using gain $rel_i$ and position discount:

$$\mathrm{DCG@k} = \sum_{i=1}^{k} \frac{2^{rel_i} - 1}{\log_2(i+1)}, \qquad \mathrm{nDCG@k} = \frac{\mathrm{DCG@k}}{\mathrm{IDCG@k}}$$

Define relevance labels consistently — binary vs graded changes scores. See retrieval overview.

Retrieval vs end-to-end RAG
  • Retriever-only eval — Recall@k / nDCG on qrels (query–document relevance judgments).
  • Reader eval — EM/F1 on answer with gold passage provided (upper bound) vs full RAG (retriever + LLM).
  • Answer faithfulness — citation match, NLI vs retrieved chunks (grounding).
Embeddings & contrastive training
  • InfoNCE / triplet loss — train metric; track loss plus retrieval Recall@k on a val query set.
  • MTEB-style benchmarks — aggregate retrieval/classification/clustering; use domain slice that matches your product.
  • Regression gate: fixed set of queries with expected neighbor ids (representations).
Chooser
  • Pretrain → eval PPL + small downstream slice; not PPL alone.
  • SFT chat → masked val CE + golden task EM/F1 + spot human eval.
  • RLHF / PPO → KL + reward + blind win rate vs SFT; watch reward hacking.
  • DPO → val pair accuracy + generation win rate.
  • RAG retriever → Recall@k / nDCG on labeled qrels; separate answer faithfulness.
  • Imbalanced classifier → PR-AUC + F1 at operating threshold, not accuracy alone.
