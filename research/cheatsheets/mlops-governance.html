MLOps — governance & lineage

Governance in one sentence

Governance answers who may use which data and models, what changed, and what you can show an auditor. It overlaps security and MLOps; this page focuses on ML-specific lineage and release discipline, not TLS or OAuth mechanics.

Lineage

Lineage is the chain from raw data → transforms → train run → registered artifact → deployment → prediction log (where policy allows). When a user reports a bad answer, you should trace model version, index version, and prompt template without guessing.

  • Store run id, git commit, data snapshot id, and container digest on every registry version (registry).
  • Log model version on each inference request (header or internal trace).
  • For RAG, log retrieved chunk ids — not necessarily full text if PII-sensitive.
Access & data handling
Training data

Restrict buckets and tables by IAM role; training jobs should use service accounts with least privilege. Do not copy production PII into unlabeled dev buckets “for a quick experiment.” Redact or hash before logging examples to W&B (cloud egress and retention policies apply too).

Models & prompts

Control who can promote registry stages and who can change system prompts in prod. Separate read-only analysts from deployers; use break-glass for emergency rollback with audit log. Agent tools need the same AuthZ as normal APIs (agent security).

Compliance-oriented practices
  • Model cards / datasheets — intended use, limitations, eval slices, known biases (especially for customer-facing LLMs).
  • Change control — prod promotion via ticket or PR with eval diff attached.
  • Retention — how long you keep prompts, outputs, and logs; align with legal hold and GDPR-style deletion requests.
  • Third-party models — license terms for fine-tune and serve; API data use policies for closed models.

High-risk domains (health, credit, hiring) need domain-specific rules; this sheet stays generic — pair with legal review.

Incident response (ML-flavored)

For a quality or safety incident: identify registry version and deploy time, rollback if deploy-correlated, freeze further promotions, preserve logs for analysis, and add failing cases to golden eval. For suspected data poisoning or prompt injection at scale, treat as security incident — see trust & policy and security sheets.

Chooser

Internal tool only → lightweight lineage (run metadata + git) may be enough. Enterprise or regulated → registry stages, IAM on data, retention policy, model cards, and monitored promotion approvals. Multi-tenant SaaS → tenant isolation in data, indexes, and logs is non-negotiable (AuthZ).
