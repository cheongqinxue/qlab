Security & access control

Foundation
Authentication vs authorization

Authentication (AuthN) answers: who is this caller? The backend verifies a password, session, or signed token with the identity provider (IdP) — the service that ran login (Google, Firebase Auth, Auth0, etc.).

Authorization (AuthZ) answers: given that identity, may they perform this action on this record? Login proves identity; it does not prove they may open invoice #42.

  • AuthN only → any logged-in user can hit any id (common breach)
  • AuthZ only → you might apply rules to the wrong person if identity was spoofed
Principles (defaults)
  • Deny by default — explicit allow rules only
  • Least privilege — smallest scope/role that works
  • Fail closed — AuthN/AuthZ errors → 401/403, not anonymous fallback
  • Defense in depth — gateway + app + DB row policies where needed
  • Secrets in env / vault — never in code, logs, or client bundles
Authentication patterns
Proof of identity
  • Password — store slow hash (argon2/bcrypt), never plaintext
  • MFA (multi-factor authentication) — second factor: TOTP app, WebAuthn/passkeys, or push
  • SSO (single sign-on) — one corporate login via OpenID Connect (OIDC) or SAML to the company IdP
  • Service accounts — machine identity (OAuth client credentials, cloud IAM roles), not human passwords
How the token reaches your API (typical consumer app)
  1. User signs in via IdP (redirect or SDK — e.g. Google, Firebase).
  2. Client holds a JSON Web Token (JWT) or session reference after login.
  3. Each API call: client sends Authorization: Bearer <token> or an HttpOnly session cookie.
  4. Your backend verifies with the IdP (public keys / Admin SDK) — every request, not once at login.
  5. Handler runs AuthZ: roles/scopes plus “does this row belong to this user?”
Sessions vs bearer tokens
  • Server session — opaque cookie points at server-side session store; easy to revoke; browser sends cookie automatically
  • JWT (JSON Web Token) — signed JSON; backend checks signature, issuer (iss), audience (aud), expiry (exp)
  • Expiry — short-lived access/ID token proves identity now; refresh token or long session reduces how often the user sees the login screen
  • Expiry is not permission — it only limits how long stolen credentials work
AuthZ — not just a permission list

Role-based access control (RBAC) maps roles to permissions (e.g. admin → users:delete). That is one layer.

Object-level checks are separate: load the row, compare user_id or tenant_id to the verified identity. Changing /items/5 to /items/6 must not work unless allowed.

Patterns (RBAC, ABAC, ReBAC) are concepts; you implement them in code, in policy engines (OPA, Cedar, SpiceDB), or in Postgres row-level security (RLS).

OAuth 2.0 / OIDC (user delegated access)

OAuth2 — authorization (access to APIs). OIDC — identity layer (ID token with sub, email claims). Public clients (SPAs, mobile) use authorization code + PKCE, not implicit flow.

API keys vs user tokens
  • API key — shared secret; good for server-to-server, scripts; rotate, scope, rate-limit
  • User OAuth token — acts as user; needs scopes and consent
  • Never expose service keys in frontends; keys ≠ substitute for AuthZ checks
Authorization models
RBAC (role-based)
  • Users → roles → permissions (e.g. billing:read)
  • Simple admin consoles; risk: role explosion, coarse grants
  • Static roles in code/DB; check on every mutating handler
ABAC & ReBAC
  • ABAC — policies on attributes (user dept, resource owner, time, IP)
  • ReBAC — graph relations (Google Zanzibar): “viewer on folder → viewer on file”
  • Use when RBAC matrices become unmaintainable (sharing, org hierarchies)
  • Engines: OPA/Rego, Cedar, SpiceDB — evaluate centrally or embed SDK
ACLs & scopes
  • ACL — list of principals allowed on one resource (good for documents)
  • OAuth scope — coarse capability string (files:write); map to internal permissions
  • Scopes alone are not enough — still enforce object-level checks (see BOLA)
API & multi-tenant
OWASP API top risks (access)
  • BOLA (broken object level authorization) — change /users/123 to /users/124 and read another user’s data
  • BFLA (broken function level authorization) — call an admin-only route without the admin role
  • Fix: resolve resource ID → load row → compare tenant_id / owner to principal from token
  • Never trust client-sent tenant ID without matching signed claim
Postgres row-level security (RLS) — own rows only

RLS lets Postgres hide rows that fail a policy. For “users see only their rows,” add user_id on the table (or organization_id plus a membership table for teams). The app sets the current user id on the DB session after AuthN; policies compare it to the row. 

ALTER TABLE items ENABLE ROW LEVEL SECURITY;
CREATE POLICY items_own ON items FOR ALL
  USING (user_id = current_setting('app.current_user_id')::uuid);

Shared documents need a grant/membership table in the policy, not only user_id on every row. RLS backs up the app; AuthN still happens in the API.

Multi-tenant isolation
  • Tenant — one customer organization; tenant id in token claim → filter every query
  • RLS on organization_id when cross-tenant leakage would be catastrophic
  • Separate database only when compliance requires hard isolation
  • Background jobs and caches must carry tenant context
Service-to-service
  • mTLS — both sides present certs inside mesh/VPC
  • Workload identity — cloud IAM (AWS IRSA, GCP SA, K8s SA → JWT)
  • Short-lived tokens; no long-lived shared passwords between services
Operations & review checklist
Enforcement points
  • Edge/gateway: AuthN, rate limits, WAF
  • App middleware: map credential → principal + roles/scopes
  • Handler: object-level AuthZ before read/write
  • DB: RLS or policy for defense in depth
Logging & audit
  • Audit log: who, action, resource id, outcome, correlation id
  • Never log passwords, tokens, API keys, full Authorization headers
  • Redact PII by default; retention policy for compliance
Web cookies & CORS
  • Session cookies: HttpOnly, Secure, sensible SameSite
  • Do not use Access-Control-Allow-Origin: * with credentialed requests in production
  • CSRF: same-site cookies + tokens for state-changing browser forms
Design review prompts
  • What happens if token is stolen? (revocation, short TTL, binding)
  • Can user A infer user B’s data from IDs or errors?
  • Are admin paths separated and MFA-gated?
  • Is AuthZ tested (negative cases), not only AuthN login tests?
