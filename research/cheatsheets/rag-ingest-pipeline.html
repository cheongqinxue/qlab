RAG ingest pipeline (ETL)

What this pipeline does

Ingest is offline ETL: sources become searchable chunks in the vector index (and usually a lexical index for hybrid RAG). It runs on webhooks, schedules, or backfill jobs — not on the user query path. When ingest lags or corrupts data, chat answers are stale, empty, or poisoned regardless of query-time tuning — retrieval, fusion, evaluation.

Normal pipeline — stages and typical stack
End-to-end flow

A document change triggers a work item (source id, version, operation: upsert or delete). Workers move it through parse → chunk → embed → index write. An orchestrator coordinates scheduled full reindexes and “delete old version after new version succeeds.” Raw files stay in object storage; the index stores chunks + vectors + metadata only.

Small team shortcut: S3 event → Lambda or Celery worker runs stages 5–11 in one process; nightly Airflow DAG reconciles counts. Scale-out: Kafka topic per source type, worker pools per stage (parse-heavy vs embed-heavy), embed service behind a GPU or API autoscale group.

Job state and idempotency

Persist per-document or per-batch state in Postgres (or equivalent): pending, parsing, embedding, indexed, failed, quarantined. Queues are at-least-once — workers use deterministic chunk_id = hash(source_id, version, index) and upsert semantics so duplicate messages do not create duplicate search results. Track content hash to skip re-embed when text unchanged. On embed model upgrade, run a versioned collection or full re-embed before alias swap — ANN.

Freshness and conflicting versions

Retrieval cannot tell which of two similar chunks is current. Give the index what it needs to decide, and settle conflicts at ingest time instead of leaving them to the model.

  • Metadata per chunk: version, effective_date, status (active, superseded, retracted), supersedes (id of the replaced document), review_by, and the source authority tier.
  • Supersede on update. When a new version is indexed, mark the old chunks superseded (or delete them) in the same job. Queries filter to status = active; policy questions that depend on a date filter on effective_date.
  • Detect conflicts at ingest. Compare each new chunk with its nearest existing chunks from other sources or versions; flag pairs that are close in meaning but state different values (a window of 30 days against 90). Route flagged pairs to review or to a rule.
  • Resolve by rule, in this order: source authority (system of record over wiki over chat export), then effective date, then ingest time. If the rule cannot decide, keep both, label them with source and date, and escalate.
  • Expire what nobody owns. Documents past review_by are flagged or down-ranked until an owner re-confirms them.
  • At answer time, if retrieved chunks still disagree, the prompt tells the model to state the conflict and cite both sources instead of merging them. See conflicting chunks.
  • Measure it: index freshness lag (source change to searchable), count of active conflicts, and a conflict slice in the evaluation set (RAG evaluation).
ETL security best practices
Trust and provenance

Every chunk carries source id, publisher, ingest time, content hash, and ACL fields used at query time. Only authenticated connectors may write; map corporate identity to allowed collections. Treat all parsed body text as untrusted until reviewed for high-trust tiers (employee wiki vs public upload). Version documents so legal hold and deletion propagate: tombstone in index when source is removed, not only delete from object storage.

Parsing and normalization

Strip scripts, hidden HTML, and comments that hide injection strings. Normalize Unicode and whitespace so detection rules are stable. Reject or quarantine files that fail size limits, encrypted PDFs you cannot scan, or formats that execute code on parse. Run prompt-injection and malware classifiers on extracted text before embed; quarantine queue for human or second model review on scores above threshold — do not rely on a single pass. See attack patterns on GenAI attack vectors.

Embedding and index writes

Use deterministic chunk ids derived from (source_id, version, chunk_index) so re-ingest is idempotent upsert, not duplicate vectors. Pin embedding model version in metadata; full re-embed when the model changes. Separate collections or namespaces per tenant where the product requires isolation; enforce write ACL on the ingest API so one tenant cannot upsert into another’s index.

Secrets and downstream LLM calls

Ingest may call LLMs for contextual retrieval headers or enrichment. Never send raw secrets from source files to external APIs without redaction; use the same DLP as production chat. API keys for embedders live in workers, not in job payloads logged to queues.

Diagnostic order (when “KB is stale or wrong”)
  1. Searchable lag — is the pipeline slow globally or one source?
  2. Queue age + DLQ — backlog vs poison docs?
  3. Stage timings — parse vs embed vs upsert bottleneck?
  4. Spot check — pick failing source_id: raw blob → parsed text → chunk in vector DB?
  5. Reconciliation — chunk count vs CMS; version field mix?
  6. Query path — if ingest healthy, switch to hallucination diagnosis (retrieval/generation).
Break-glass

Full re-embed into a new collection + alias swap when incremental repair is slower than SLA. Freeze writes during swap or use dual-write with read from old alias until verification passes. Run retrieval smoke tests from RAG evaluation golden set before cutting traffic.
