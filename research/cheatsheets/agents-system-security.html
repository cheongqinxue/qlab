Agents — system & security design

Issue vs tool

The issue is that agents act in the world: tools, credentials, and user data can be abused via model output or injected text. Fixes are mostly system design — allowlists, AuthZ on tools, sandboxes — not a single classifier. Policy moderation does not stop bulk email if SMTP is wired with admin creds. Grounding does not stop prompt injection in a PDF.

Action abuse & tool surface
Least privilege
  • Tool allowlist — no arbitrary fetch unless sandboxed.
  • Scoped credentials — per-user OAuth, read-only DB — not master keys in the agent process.
  • Side-effect tiers — writes need HITL (graph checkpoints).
  • Budgets — step/token caps (reliability).
Harness validation

Parse tool JSON against schema; parameterized SQL; isolated code workers. The harness enforces AuthZ — not the model.

Prompt injection
Direct vs indirect
  • Direct — user overrides system instructions.
  • Indirect — instructions in RAG, email, web, or tool output in context.

Mitigations: separate instruction vs data channels, delimit untrusted blocks, sandbox browsing, never execute RAG text as code.

Agent patterns
  • Mark tool results as untrusted data.
  • HITL when retrieved text triggers high-impact actions.
  • Avoid poisoning long-term memory with unverified tool text.
Identity, secrets, supply chain
Tenancy & AuthZ

Propagate user id into retrieval and tools. The LLM is not an AuthZ bypass (AuthN vs AuthZ).

Secrets, logging, sandbox
  • Secrets from vault/env only; redact trajectories for training.
  • CodeAct / browser agents: ephemeral VMs, allowlisted egress.
  • MCP/plugins: untrusted servers; pin tool schemas at deploy.
Chooser
  • Read-only Q&A → injection defenses + retrieval ACL; minimal tools.
  • Ops agent → allowlist, HITL on writes, user-scoped creds.
  • Autonomous customer agent → assume hostile input; no single-shot high-impact actions.
