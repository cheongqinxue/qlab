Agents — memory & state

Why memory is its own topic

An agent’s control pattern (ReAct, graph, planner) decides what happens next. Memory decides what the model is allowed to see when it decides — chat history, tool outputs, user profile, past failures, reusable skills, and retrieved documents. Most production incidents are context mistakes (stale facts, wrong thread, unbounded logs), not wrong loop syntax.

Three layers (mental model)
Working memory

Everything in the current prompt: system instructions, user messages, tool observations, scratchpad notes. Bounded by the context window; expensive if you paste entire tool logs every step.

  • Compaction — summarize older turns; keep last-k raw tool outputs.
  • Structured state — JSON artifact (plan, extracted fields) smaller than full chat replay.
  • Graph checkpoints — persist working state between runs (state machine nodes).
Episodic memory

Records of past episodes: prior sessions, successful trajectories, error traces, “what we tried on ticket #4821.” Usually stored outside the model weights — vector DB, event log, or document store — and retrieved when a new task looks similar.

  • Keyed by user, project, or tenant — never leak episodes across ACL boundaries.
  • Often paired with embeddings over (goal, outcome, tools used) tuples.
  • Reflexion-style critiques are episodic hints for the next retry (patterns).
Semantic memory

Stable facts and reusable skills: user preferences, API quirks, “always use read-only DB role,” or a library of verified code snippets. Updated less often than chat; should be versioned and auditable.

  • Skill libraries — e.g. Voyager-style stored programs that solved a class of environment tasks.
  • Profile / prefs — short bullet summaries maintained by a background job, not raw chat dumps.
  • Distinct from RAG corpus — semantic memory is agent-centric; RAG is org documents (RAG systems).

Context management strategies
The problem

Every agent step pays for all tokens currently in the prompt. Tool dumps, long chats, and repeated system text add cost, latency, and lost-in-the-middle failures (models overlook facts buried mid-prompt). Context management is the harness job: decide what stays in-window, in what shape, and what moves to external memory — independent of which control pattern you use.

Truncation & sliding window

Keep the last N user–assistant turns (or last M tokens) and drop the rest. Cheapest strategy; good for stateless chat.

  • Always preserve system + current task spec — never truncate the only copy of the goal.
  • Prefer dropping middle tool spam while keeping first setup + recent observations (sandwich) when logs allow.
  • Weak for long projects unless paired with summaries or external state.
Rolling & hierarchical summarization

A side model (or the same LLM on a schedule) writes a running summary of older turns; the prompt becomes summary + recent verbatim messages. Hierarchical: summarize chunks, then summarize summaries for month-long threads.

  • Extract decisions, open questions, constraints explicitly — generic “they discussed X” summaries lose actionable detail.
  • Re-summarize when summary length exceeds a budget; keep a short immutable “contract” block (IDs, dates, user hard rules).
Structured state instead of chat replay

Replace growing message history with a JSON artifact: plan steps done/pending, extracted entities, last tool errors, citation ids. The model sees state + last k messages, not every Thought/Action/Observation line ever emitted.

  • Natural fit for plan-and-execute and graph checkpoints (state machines).
  • Handoffs between sub-agents pass the artifact, not full sibling traces.
Tool observation shaping

Raw tool output is often the biggest token hog. Shrink before it hits the model:

  • Truncate + pointer — first/last lines + “full log id 7f3a in store.”
  • Structured extract — SQL → rows as table or aggregates; HTML → main text; PDF tool → cited spans only.
  • Progressive disclosure — list files, then read one file on demand; never paste whole repo trees.
  • Deterministic post-process — regex/JSON parse beats asking the LLM to “ignore the noise.”
Retrieval budgeting (RAG + memory)

Retrieval adds context on purpose — cap it so it does not crowd out reasoning:

  • Fixed top-k and max chars per chunk; rerank then cut (retrieval stages).
  • Query-conditioned fetch each step, not one mega-retrieval at session start (stale for agents).
  • Separate slots: corpus RAG vs episodic memory hits — label sources so the model does not merge them.
Priority tiers & token budget

Assign a budget (e.g. 8k tokens) and fill in order until full:

  1. System + safety + tool schemas (stable → good for prefix caching on some APIs).
  2. Current user goal and constraints.
  3. Structured state / rolling summary.
  4. Fresh tool observations and retrieved chunks.
  5. Oldest chat tail — first to drop or summarize.

Long-context models (128k+) reduce emergencies but still cost linearly — budgeting remains an ops lever.

Compression & routing (optional)
  • Prompt compression (LLMLingua-class) — drop low-salience tokens in filler text; test on your tool formats.
  • Small model condenser — cheap model shrinks logs; frontier model plans next action.
  • Sub-agent isolation — workers get task-local context; supervisor merges short reports only.

Patterns & systems
MemGPT-style virtual context

Treat the context window like RAM and external stores like disk. The agent (or harness) explicitly pages content in and out: archive a long tool log to storage, fetch a summary or chunk when needed. Same frozen LLM; the innovation is memory management policy — when to write, what to evict, what to retrieve. Implements several strategies above (paging, summarization, retrieval) as first-class agent actions.

Generative Agents–style reflection

Periodic reflection over recent events produces higher-level summaries (“user is preparing a launch”). Importance scoring decides what enters long-term store vs is forgotten. Useful for simulations and long-horizon personal assistants; needs guardrails so inferred traits are not treated as ground truth.

Temporal & graph memory

Some stacks keep time-stamped facts and entity edges (who said what, when a doc changed) so retrieval respects recency and contradiction. Helps “what did we decide last Tuesday?” without stuffing full chat into every prompt. Implementation varies (SQL + embeddings, graph + LLM extraction); pattern is structured recall + semantic search.

Skill & procedure stores

After a successful episode, extract a named procedure (code, API sequence, checklist) into a library. New tasks retrieve similar skills and adapt them — learning without weight updates. Quality depends on verification before promote-to-library (learning sheet).

Engineering checklist
What to store per episode
  • Goal, final outcome, success/failure signal, tools called, latency, model version.
  • Hashes of retrieved chunks (for RAG debug) — not necessarily full text if ACL-sensitive.
  • Optional: user-approved summary for long-term semantic memory.
Failure modes
  • Context stuffing — every observation forever → cost, distraction, lost needle facts.
  • Stale semantic memory — old prefs contradict new instructions; need TTL and user override.
  • Cross-tenant bleed — episodic retrieval without strict filters.
  • Poisoned memory — attacker plants a “lesson” that future sessions retrieve (security).
Chooser
  • Short tasks, single session → working memory only + tight compaction.
  • Returning users / long projects → episodic + semantic stores with retrieval tool.
  • Large org knowledge → RAG corpus; agent memory holds session-specific residue only.
  • Repeated environment tasks → verified skill library before fine-tuning the base model.
  • Improve over time → pair memory with offline learning pipeline (learning & improvement).
