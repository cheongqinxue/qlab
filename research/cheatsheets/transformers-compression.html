qlab cheatsheets

Quantization math, PTQ/QAT, formats, pruning, and what hardware actually runs. Serving context → efficiency.

Transformers — compression

What we compress
  • Weights — largest static footprint (7B FP16 ≈ 14 GB); main target for INT4/FP8 checkpoints.
  • Activations — matter for training memory and for W8A8 / FP8 inference (matmul inputs must match kernel support).
  • KV cache — runtime buffer at decode; own quant knob — KV quant tile (not the same as weight INT4).
  • Pruning — remove weights or structures; can combine with quant (sparse + low-bit).

Vector index PQ/SQ is a different “quantization” — see ANN sheet. Here: neural network weights and activations.

Quantization math (affine)
Encode & decode

Quantization maps a floating tensor $x$ to low-bit integers $q$, with scale $s$ and optional zero-point $z$ (asymmetric):

$$q = \mathrm{clip}\left(\left\lfloor \frac{x}{s} \right\rceil + z,\; q_{\min},\, q_{\max}\right), \qquad \hat{x} = s \cdot (q - z)$$

Symmetric (common for weights): $z=0$, $q_{\min}=-2^{b-1}$, $q_{\max}=2^{b-1}-1$ for $b$-bit signed INT. Asymmetric: $z$ shifts the bin grid when values are not centered on zero (often activations).

Granularity
  • Per-tensor — one $(s,z)$ for the whole matrix; simplest, worst error on outlier channels.
  • Per-channel — one scale per output channel (row of weight); default for INT8/INT4 weights in LLMs.
  • Block-wise — scale every $g$ consecutive elements (GPTQ/AWQ blocks); balances tables vs accuracy.
  • Group size — smaller groups → more scales stored → better SNR, slightly larger file.
Integer matmul (why formats differ)

Idealized INT8 dot-product uses integer accumulators then rescales: $\hat{y} = s_x s_w \sum q_x q_w$. Hardware may require symmetric weights, channel scales, or FP8 paths with fused scale vectors. If the runtime only supports weight-only INT4, activations stay FP16/BF16 and weights are dequant on the fly inside the kernel — still a win from bandwidth.

Weight quant vs activation quant
Weights

Static after training: same matrices every forward pass. Outliers are per-channel and predictable — INT4/INT8 weight-only (GPTQ, AWQ, GGUF) works well because activations stay high precision.

  • Compresses model size and weight bandwidth (often the decode bottleneck).
  • Scales usually per output channel or per block; computed once in PTQ.
  • Does not reduce activation RAM during a long prefill unless you also quant activations.
Activations

Dynamic range per layer and per token: strong outliers (attention logits, FFN intermediates) make naive INT8 activations hard. Quantizing activations enables true W8A8 integer GEMMs and smaller activation footprints — but errors compound through depth.

  • Need calibration or QAT; scales may be static (fixed from sample batches) or dynamic (see below).
  • Transient layer outputs during prefill are activations; stored K/V past tokens are the KV cache — see KV quant.
  • Weight-only W4A16 avoids this pain: matmul is effectively dequant(weights) × FP16 activations in one fused kernel.
Naming: W4A16, W8A8, …

KV cache quantization
What the KV cache is

At decode (one new token per step), self-attention needs keys and values for every past token. The runtime appends projected K and V tensors per layer instead of recomputing them — the KV cache. It is not part of the checkpoint; it is allocated per request and grows with seq_len × batch × layers.

Rough bytes (FP16/BF16) per layer: $2 \times n_{\mathrm{kv\_heads}} \times d_k \times \mathrm{seq\_len} \times \mathrm{bytes\_per\_elem}$. Full stack × $L$ layers — see efficiency — KV size. Weight-only INT4 shrinks the model file but does not shrink this buffer unless you separately quantize stored K/V.

Why KV quant exists
  • Decode is bandwidth-bound — each step reads the entire past KV from memory; halving bytes ≈ halving that traffic (when kernels support it).
  • Long context — KV can exceed weight RAM for multi-user or 100k-token sessions; KV quant is a serving lever, not a training artifact.
  • Complements GQA / MLA — fewer heads or latent KV reduces size; quant reduces bytes per stored element. Stack both when available.
What you quantize

After $K = X W_K$ and $V = X W_V$ (or MLA latent then up-project), the cached tensors are cast to low precision for storage. On each decode step, the new query $Q$ attends over stored $\hat{K}, \hat{V}$ — either via dequant inside the attention kernel or FP8/INT8 SDPA paths that fuse scale.

  • K and V separately — may use different scales or dtypes per tensor type in some runtimes.
  • Granularity — often per token (scale when the slot is written at prefill or append) or per head / per block within the cache line.
  • MLA — if the cache holds compressed latents $c^{KV}$, quant applies to that smaller tensor before expand — extra savings vs full-head KV.
Formats & static scales
KV dtype Size vs FP16 Typical notes
FP16 / BF16 1× baseline Default; no extra scale metadata
FP8 (e.g. E4M3) ~2× smaller Common on Hopper+ serve stacks; per-tensor or per-token scale
INT8 ~2× smaller Affine $s,z$ per block/token; watch attention softmax sensitivity
INT4 / NVFP4 (KV) ~4× smaller Emerging in vendor recipes; stronger quality risk on very long ctx

KV quant is almost always static at write time: when token $t$ is processed, compute scale from that token’s K/V (or block), store $(q, s)$ in the cache slot. You do not re-run full calibration offline — scales are online but fixed per slot once written. That differs from dynamic activation quant on transient tensors, which recomputes scale every forward on the same logical tensor shape.

Accuracy & eval
  • Errors in $\hat{K},\hat{V}$ bias attention weights — hurts long-range retrieval (needle-in-haystack) before short-chat quality moves.
  • Ablation: same prompt at 4k / 32k / 128k with KV FP8 vs FP16; watch RAG cite drift if KV quant is on in prod.
  • Prefill often stays FP16 for the new token’s projections; only cache storage dtype changes — confirm your engine’s policy.
Runtime & toggles
  • vLLM — FP8 KV and related cache dtypes (model/GPU dependent); must match checkpoint and CUDA capability.
  • TensorRT-LLM — FP8/INT8 KV options in build config; fused kernels vary by head size.
  • llama.cpp — primarily weight quant; KV often FP16 unless specific build flags / backends.
  • Mismatch → engine falls back to FP16 cache (safe) or refuses load — always read release notes for dtype pairs.

Chooser: long multi-turn or big batch decode → enable KV FP8/INT8 after GQA/MLA; keep weight quant separate; eval long-context tasks.

Static vs dynamic quantization
Static

Scale and zero-point fixed after offline calibration (representative prompts, C4 slice, your RAG queries). At inference: same $s, z$ every token — fast, predictable, works on NPUs and TRT-style compilers.

  • Best for: weights, and activations when distribution is stable layer-to-layer.
  • Risk: calibration domain mismatch (code-heavy calib, chat-heavy serve) → silent quality drop.
  • PTQ default for GPTQ/AWQ weight scales; SmoothQuant produces static per-channel scales for W8A8.
Dynamic

Scales computed at runtime from the actual activation tensor (per batch, per token, or per block): $s = \max(|x|)/q_{\max}$ on the fly. No calib file for that tensor — adapts to outlier tokens.

  • Best for: activations with heavy tail outliers when you still want INT8 math.
  • Cost: extra reduction (max/absmax) each layer — small overhead vs matmul, but harder to fuse on some NPUs.
  • PyTorch torch.quantized dynamic LSTM/Linear patterns; LLM serve stacks often prefer static W8A8 after SmoothQuant for peak throughput.
When to pick which
  • Ship INT4 weights on consumer GPU → static weight scales (GPTQ/AWQ); activations FP16.
  • Max INT8 GEMM on H100 → static W8A8 (SmoothQuant or QAT); dynamic activations only if accuracy fails static.
  • Exploratory accuracy rescue → try dynamic activation quant on failing layers before abandoning INT8.
Hessian-aware compression
What the Hessian is (plain language)

When you train a model, the gradient tells you which direction to nudge each weight to reduce the loss on the next step. The Hessian is the next level up: it describes curvature — how sensitive the loss is when you change one weight, two weights together, or many at once. A flat direction in the loss landscape means small weight changes barely hurt quality; a sharp direction means a tiny mistake in one weight can cost a lot unless neighboring weights are adjusted to compensate.

For a layer with millions of weights, the full Hessian would be a gigantic matrix (one row and column per weight). Nobody stores that for an LLM. Hessian-aware compression methods still borrow the idea: they use a local quadratic picture of the loss around the current weights to decide what to remove or round and how to fix the survivors so the layer’s output stays close to the original on real calibration prompts.

What that delivers: better one-shot INT4 weights (GPTQ) and less perplexity blow-up when you zero out many weights at once (SparseGPT, OWL) compared with “drop the smallest |weight| and hope for the best.” Magnitude-only rules treat every weight as equally important; Hessian-aware rules ask “if I distort this weight, how much does the loss actually move on the data I care about?”

Why it is expensive

Hessian-aware algorithms need a calibration pass: forward (and sometimes backward) passes on hundreds or thousands of tokens so the method can estimate curvature from activations and errors. That is already non-trivial on a 70B model.

  • A exact Hessian for one linear layer scales with the square of its parameter count; storing or inverting it is infeasible at LLM width.
  • Even a block inverse used while processing weights in order still costs heavy linear algebra (Cholesky-style updates) per column or block — much slower than round-to-nearest or magnitude pruning.
  • Memory spikes during offline compression: you hold layer weights, activation statistics, and temporary inverse factors; multi-GPU sharding helps but the job remains a batch offline step, not something you run on every deploy.

Drawback in practice: strong accuracy per bit, but slow, memory-hungry PTQ/prune jobs and more moving parts than AWQ-style activation scaling. Teams accept that trade when INT4 quality matters; they skip it when RTN or AWQ is good enough.

Approximations researchers use

Methods never use the full global Hessian. They use cheap stand-ins that capture “which directions hurt” on calibration data:

  • Gauss–Newton / Fisher picture — for a linear layer, curvature is often approximated from outer products of activations ($H \approx X^\top X$ in spirit). That matches the classical Optimal Brain Surgeon intuition without building a billion-by-billion matrix.
  • Diagonal or block-diagonal — only keep curvature along the weight column or block you are quantizing or pruning right now; ignore cross-talk elsewhere. GPTQ and SparseGPT process weights sequentially and maintain a running inverse for the current block only.
  • Empirical Fisher — use squared gradients on calib batches as a diagonal importance score; common in structured pruning research (related to the Fisher row in the tools table below).
  • Cheaper proxies (not full Hessian) — Wanda scores $|w_{ij}| \times \|x_j\|$ (weight times activation norm). No matrix inverse; much faster, slightly weaker at high sparsity, but often “good enough” for a first mask.

Mental model: Hessian-aware code is error compensation — quantize or delete a weight, measure the local linear/quadratic knock-on effect, nudge remaining weights to cancel it. Approximations trade exact curvature for something you can compute in hours, not years.

PTQ vs QAT
PTQ — post-training quantization

Start from a trained FP16/BF16 model; choose scales (and maybe clip outliers) using a small calibration set — no full retrain.

  • RTN (round-to-nearest) — fast baseline; weak at INT4 without extra steps.
  • GPTQ — layer-wise Hessian-aware compensation after INT4 rounding; strong weight-only PTQ.
  • AWQ — scale salient weight channels using activation statistics; fast INT4 serve.
SmoothQuant (W8A8 PTQ)

Problem: LLM activations are harder to INT8-quantize than weights (outliers in FFN and attention). SmoothQuant (MIT/Hao et al.) applies an equivalent per-channel transform before quant: for smoothing factor $s_j \ge 1$ on channel $j$,

$$Y = X W \quad \Rightarrow \quad Y = \underbrace{(X \oslash s)}_{\text{easier to quant}} \cdot \underbrace{(s \odot W)}_{\text{absorbs scale}}$$

($\oslash$ = divide activations by $s$, $\odot$ = multiply weights by $s$.) Mathematically identical in FP32; numerically, you shrink activation dynamic range and widen weight range so both fit INT8 static grids after calibration. $s_j$ is chosen from activation magnitudes (migration strength hyperparameter trades weight difficulty vs activation difficulty).

  • Output: static INT8 weights + static activation scales → friendly to TensorRT, torchao, NVIDIA ModelOpt flows.
  • Does not replace INT4 weight-only paths — it targets W8A8 throughput, not 4-bit storage.
  • Often paired with per-token or per-tensor activation quant policies in the runtime — verify your exporter’s spec.
QAT — quantization-aware training

Insert fake quant (quantize → dequantize) in the forward pass during training or a short fine-tune so weights adapt to rounding.

  • STE (straight-through estimator) — backward ignores quant step; standard trick.
  • Learned scales — $s$ can be trainable parameters per channel/block.
  • When worth it — INT8 W8A8 at scale, edge deployment with tight accuracy budget, or FP8 pretrain recipes.
  • Cost — more training time than PTQ; often best quality at same bit width.
Pruning
Unstructured vs structured
  • Unstructured — zero individual weights by importance score. High sparsity % but irregular pattern.
  • Structured — drop heads, FFN dims, layers, or MoE experts → smaller dense shapes.
  • N:M semi-structured — e.g. 2:4 (two zeros per four weights); NVIDIA sparse Tensor Cores on Ampere+.

Do people prune production LLMs?

Rarely at frontier scale compared to quantization and distillation. Reasons:

  • Unstructured sparsity — 50% zeros does not halve latency unless kernels skip zeros; dense checkpoints + INT4/FP8 usually win on ops complexity.
  • 2:4 sparse — real speedups on NVIDIA, but extra training/sparsity pipeline and accuracy tuning; less universal than AWQ/GPTQ across hardware.
  • Structured prune (drop layers/heads) — works in research and for bespoke small models; changing shape breaks standard weight formats and many serve runtimes unless you ship a custom checkpoint.
  • MoE — “prune experts” is emerging, but routing and EP serving make it a research/integration problem, not default ops.
  • What teams actually do — INT4/FP8 quant, smaller dense models (distill/Chinchilla-optimal), speculative decoding, GQA/MLA — predictable tooling and vendor support.

When pruning still makes sense: you control the full stack (custom CUDA), need 2:4 on Ampere/Hopper, academic compression benchmarks, or structured shrink to a fixed edge budget where no small base model exists. Otherwise quant + right-sized model is the default playbook.

Pruning + quant order
  • Prune → recover FT → GPTQ/AWQ — common experiment order for unstructured.
  • Quant then prune — can destroy saliency estimates; compare both on your metric.
  • Always eval task accuracy, not perplexity alone.

What “supported” really means

A checkpoint bit width is not enough — you need a kernel + runtime that implements that layout on your device. Mismatch → silent dequant to FP32 (slow) or load failure.

Checklist before ship
  • Same tokenizer + chat template as FP baseline.
  • Eval perplexity and task metrics (MMLU slice, your RAG hit rate) — quant hurts tail behaviors first.
  • Confirm max context with quant KV if enabled.
  • Pin runtime version (vLLM/TRT-LLM/llama.cpp) — quant layouts tie to loader code.
  • For regulated deployments: log model hash + quant recipe (GPTQ vs AWQ, group size).
Chooser
  • Fastest path to smaller GPU RAM → AWQ or GPTQ INT4 weight-only + vLLM/llama.cpp.
  • Best INT8 throughput on H100 → FP8 or W8A8 with vendor recipe (often QAT or strong PTQ).
  • Fine-tune on laptop → QLoRA (NF4 base) + FP16 adapters.
  • Edge phone NPU → vendor ONNX/QNN pipeline; expect structured models.
  • Already memory-bound on decode → pair weight quant with KV FP8 and GQA/MLA.
  • Chasing FLOPs → structured prune + N:M if your GPU generation supports it; else quant first.
