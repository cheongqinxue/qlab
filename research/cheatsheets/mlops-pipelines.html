MLOps — pipelines & CI

Pipeline vs one-off script

A pipeline is a directed graph of steps with declared inputs and outputs: ingest, featurize, train, evaluate, register. Each step should be rerunnable from its inputs without manual copy-paste on a laptop. A one-off SSH job can prove an idea; a pipeline is how the team runs it the tenth time.

Typical DAG steps
Data & features

Pull a pinned data snapshot, validate schema, build train/val splits, and optionally write preprocessed caches (tokenized shards, embeddings). Sweeps should read warm caches so GPUs do not wait on CPU — same idea as pre-transform upfront.

Train & evaluate

Run training with a frozen config file, log to Weights & Biases (W&B) or MLflow, and emit an eval report against a golden set (metrics). Fail the pipeline if primary metric drops below a threshold compared to the current prod baseline.

Register & notify

On success, push artifacts to a registry (registry sheet) and open a review (PR, ticket, or manual approval). On failure, keep logs and tag the run so someone can diff config and data version.

CI for ML (pull requests)
  • Unit tests on data transforms and metric functions — fast, every commit.
  • Smoke train on a tiny subset (minutes, CPU or small GPU) to catch OOM and shape bugs early.
  • Compare eval on a frozen golden file to main branch; fail if regression exceeds tolerance.
  • Do not run full multi-day pretrain in CI; schedule that in scheduled pipelines or manual triggers.
Chooser

Single researcher, few models → W&B + git tags may be enough. Team shipping weekly → add registry and CI golden eval. Many parallel train jobs on cloud → SkyPilot or a pipeline runner plus shared artifact bucket.
