Hallucination — causes & diagnosis

Three terms people conflate

Hallucination (in product language) usually means the model stated something confidently that is not supported by the evidence you allowed it to use (retrieved chunks, tool JSON, policy docs). Faithfulness (or groundedness) is the metric flip side: each claim in the answer should be entailed by or quoted from that evidence. Answer correctness is whether the statement is true in the real world — you can be faithful to a wrong or outdated document and still harm users. Diagnosis always asks: was the right evidence present, did the model use it, and was that evidence itself true?

Cause taxonomy (by layer)
Retrieval layer — evidence never reached the model

Retrieval miss. The gold passage was not in top‑k, so the model answered from parametric memory. Empty or weak retrieve. Scores below threshold but the pipeline still called the LLM. Over-filtering. ACL or metadata filters removed the only relevant chunk. Stale index. Embeddings or text reflect an old policy; retrieval “succeeds” on the wrong version. These look like generation hallucinations in the UI but fix is ingest, chunking, hybrid search, or filters — see ingest pipeline, retrieval, and fusion.

Retrieval layer — evidence present but wrong or incomplete

Wrong chunk selected. Recall@k is high (gold somewhere in top five) but the prompt or reranker emphasized a similar but incorrect passage — wrong SKU, wrong policy section, adjacent paragraph without the number the user needs. Chunk boundary split. The fact spans two chunks; neither alone supports the answer the model synthesized. Conflicting chunks. Two retrieved snippets disagree; the model merges them into a fluent detail that appears in neither source. Prompt injection in sources. Indexed HTML or tickets contain adversarial “ignore policy” text; the model treats it as instructions or facts.

Generation layer — context in prompt, model still invents

Parametric override. Strong priors (common misconceptions, training memorization) outweigh provided context — typical when recall is good but faithfulness is low. Detail fabrication. Correct gist, invented specifics (dates, amounts, names) not in any chunk. Fake or sloppy citations. Citation ids that were never retrieved, or quotes that are not substrings of the cited chunk. Empty-context habit. Prompt or fine-tune encourages always answering; model does not abstain when context is thin.

Agent and tool paths

Tool hallucination. Model emits a function name or JSON args that do not match the schema or reality — harness issue as much as model issue. Observation distortion. Agent summarizes tool output in natural language and adds facts; downstream steps trust the summary. Stale tool vs fresh RAG. Numbers from an old tool call conflict with retrieved policy; the model picks one inconsistently. Long-context drift. “Lost in the middle” — evidence was in the prompt but attention-weighting effectively ignored it (hard to measure on API models; claim-level NLI is the practical test).

User and product effects (not random model noise)

Leading or sycophantic steering. User phrasing pushes the model to agree and invent supporting detail. Reasoning-model rationalization. Long internal chains that sound plausible but diverge from retrieved evidence — evaluate final answer against context, not chain eloquence. Creative mode on factual tasks. Temperature and instructions tuned for marketing copy on a support bot.

Diagnostic workflow
Step 1 — Split retrieval from generation

On a labeled or sampled query set, compute recall@k (is the gold chunk in the retrieved list?) separately from faithfulness (are answer claims supported by the retrieved text actually placed in the prompt?). If recall is low, stop tuning prompts and fix retrieval. If recall is high and faithfulness is low, the bug is chunk choice, prompt assembly, or generation. If faithfulness is high and users still complain, check correctness (stale docs, wrong tenant data).

Step 2 — Inspect traces (production or replay)

Log for every answer: query, retrieved chunk ids and scores, rerank order, model id, prompt version, and final text. For a bad answer, ask: (1) Was the gold chunk retrieved? (2) Was it in the prompt? (3) Which citation ids did the model cite? (4) Does each cited span contain the claimed sentence? Manual review of ten failures often beats a new embedding model.

Step 3 — Claim-level checks (automated)

Split the answer into atomic claims (rules or LLM extractor). For each claim, run NLI entailment or a cross-encoder against the union of retrieved passages (not against the whole internet). Count unsupported-claim rate. Optionally require every claim to link a character span in a chunk; that is stricter than citation ids alone. Tools in the RAGAS / ARES family implement variants of this; calibrate judges on human labels for your domain.

What usually does not help first

Swapping to a larger LLM before measuring recall and faithfulness. Lowering temperature alone when retrieval is empty or wrong. Attention visualization on closed API models as a primary diagnostic. Adding more chunks to context without reranking — often increases conflict and fabrication surface.

Mitigation (elsewhere)
After you know the cause

Thresholds and abstention, required citations, CoVe, NLI gates, tool-as-source-of-truth, structured output validation, and human escalation are documented on agents — grounding & hallucination.
