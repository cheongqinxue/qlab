qlab cheatsheets

Data-store families, representative products, and selection heuristics (2025–2026 positioning).

Databases by type

Category map (what “type” means)

Products overlap: MongoDB is document-first but also a general app database; DynamoDB is key-value with optional document fields; PostgreSQL spans OLTP, JSON, vectors, and time-series via extensions. This sheet groups by primary storage model and typical access pattern—not vendor marketing labels.

  • Row / relational OLTP — ACID transactions, joins, constraints, ad-hoc SQL.
  • Document — flexible JSON/BSON records, nested objects, app-centric schemas.
  • Key-value / cache — O(1) lookups by key; often in-memory or serverless.
  • Wide-column — partition-key-oriented rows; massive write throughput.
  • Columnar OLAP — scan/aggregate over huge datasets; append-heavy facts.
  • Vector — approximate nearest neighbor (ANN) over embeddings.
  • Graph — nodes, edges, traversals; relationship queries dominate.
  • Time-series — timestamped samples, retention, roll-ups, downsampling.
  • Embedded / edge — in-process or single-node; minimal ops.
  • Distributed SQL (NewSQL) — SQL + horizontal scale + strong consistency.
How to choose (quick heuristics)
  • Start from access patterns, not brand: point reads, range scans, joins, aggregations, full-text, vector similarity, graph hops, or stream ingest.
  • Consistency vs latency: need serializable cross-row transactions → relational OLTP or distributed SQL; tunable/eventual OK → Cassandra, DynamoDB, many caches.
  • Query flexibility: ad-hoc SQL/reporting → PostgreSQL or a warehouse; fixed key paths → KV/wide-column; hybrid filters + vectors → Qdrant, Weaviate, or pgvector.
  • Ops budget: managed/serverless (Pinecone, DynamoDB, Spanner) vs self-hosted (ClickHouse, Qdrant, Postgres). Embedded (SQLite, DuckDB) when the app owns the file.
  • Scale shape: billions of append-only events → columnar; billions of vectors → Milvus/Qdrant; global multi-region SQL → Spanner/Cockroach class (see cloud sheet for hosted SKUs).
  • HTAP trend (2025+): Postgres columnar/compression, ClickHouse vectors, and zero-ETL replicas reduce “OLTP + separate OLAP” sprawl—still evaluate freshness and isolation needs.
PostgreSQL (relational / OLTP + extensions)
  • Strengths: MVCC OLTP, rich SQL, mature optimizer, parallel queries, extensions (PostGIS, pgvector, Timescale).
  • Use cases: default OLTP for complex apps, mixed OLTP + reporting, geo, RAG with pgvector on one stack.
  • Indexing: B-tree, GIN/GiST/BRIN, partial/expression indexes; JSONB GIN.
  • Consistency: full ACID; serializable isolation available.
  • Query language: SQL (strong standards alignment).
  • Scaling: vertical + read replicas; sharding via Citus or app-level; connection pooling (PgBouncer).
MySQL / MariaDB (relational / OLTP)
  • Strengths: InnoDB row store, low connection overhead, huge CMS/LAMP ecosystem, mature replication.
  • Use cases: read-heavy web apps, e-commerce catalogs, simple transactional workloads at high connection counts.
  • Indexing: B-tree clustered PK (InnoDB); secondary indexes; full-text (InnoDB).
  • Consistency: ACID (InnoDB); async replicas for read scale (lag-aware reads).
  • Query language: SQL (dialect differs from Postgres—port carefully).
  • Scaling: read replicas, Vitess or manual sharding for write scale; Group Replication / Galera for HA clusters.
SQLite (relational, embedded OLTP)
  • Strengths: single-file, zero server, public domain, excellent read latency in-process.
  • Use cases: mobile/desktop, edge devices, local dev, tests, low-write embedded control planes.
  • Indexing: B-tree; FTS5; limited JSON helpers vs Postgres JSONB.
  • Consistency: ACID; WAL mode improves concurrent readers; effectively one writer at a time.
  • Query language: SQL subset with modern CTEs/window functions in recent releases.
  • Scaling: not a network OLTP tier—replicate via Litestream/backup tools; not for high concurrent writers.
MongoDB (document)
  • Strengths: flexible BSON schema, rich aggregation pipeline, multi-doc ACID, sharding, Atlas vector search + search indexes.
  • Use cases: product catalogs, content, event payloads, mobile backends, unified operational + AI features on documents.
  • Indexing: single/compound, text, geospatial, vector (Atlas); shard key drives data locality.
  • Consistency: tunable read/write concerns; replica set elections; causal consistency options.
  • Query language: MongoDB Query API + aggregation framework (not SQL).
  • Scaling: horizontal sharding (hash/range/zone); Atlas managed tiers.
Couchbase (document + memory-first KV)
  • Strengths: integrated caching layer, sub-ms KV paths, mobile sync (Couchbase Mobile), N1QL SQL-on-JSON.
  • Use cases: session stores, user profiles, travel/gaming/retail peak traffic, offline-first mobile.
  • Indexing: primary + secondary on JSON fields; full-text and vector features in platform editions.
  • Consistency: per-document; multi-node topology with separate service roles (ops complexity).
  • Query language: N1QL/SQL++ for documents; KV API for hottest paths.
  • Scaling: multi-dimensional scaling (independent query/index/data services); often paired as cache + document tier.
Redis (key-value / cache / structures)
  • Strengths: sub-ms in-memory ops, rich types (strings, hashes, streams, sorted sets), pub/sub, Lua atomicity.
  • Use cases: cache, sessions, rate limits, leaderboards, feature flags, lightweight queues, distributed locks.
  • Indexing: key-centric; RediSearch module for secondary/text (where enabled).
  • Consistency: single-threaded command path per shard; async replication—treat as cache/ ephemeral unless tuned for durability.
  • Query language: command API (no ad-hoc query engine).
  • Scaling: Redis Cluster hash slots; Redis 7+ optional multi-threaded I/O; memory-bound footprint.
Amazon DynamoDB (managed key-value / document)
  • Strengths: serverless autoscale, single-digit-ms latency, global tables, streams (CDC), on-demand billing.
  • Use cases: serverless apps, gaming state, IoT ingestion, shopping carts—workloads with stable partition keys.
  • Indexing: partition key + optional sort key; GSIs/LSIs for alternate access paths (eventual on indexes).
  • Consistency: per-item; strong reads optional; transactions across ≤25 items.
  • Query language: GetItem/Query/Scan API; PartiQL optional; no joins—denormalize in design.
  • Scaling: transparent partition scaling; watch hot partitions and item size (400 KB cap).
Apache Cassandra (wide-column)
  • Strengths: masterless ring, linear write scale, multi-DC replication, TTL rows, tunable consistency.
  • Use cases: high-velocity events, messaging metadata, time-ordered logs when query patterns are fixed upfront.
  • Indexing: primary key = partition + clustering columns; secondary indexes limited—model one table per query.
  • Consistency: ONE/QUORUM/ALL per read/write; no cross-partition transactions.
  • Query language: CQL (SQL-like syntax, wide-column semantics).
  • Scaling: add nodes for throughput; compaction/repair ops matter at scale.
ScyllaDB (wide-column, Cassandra-compatible)
  • Strengths: CQL-compatible, shard-per-core architecture, lower tail latency vs JVM Cassandra on same hardware.
  • Use cases: same as Cassandra when CPU efficiency and predictable latency matter (IoT, telco, large event pipelines).
  • Indexing: same partition/clustering model as Cassandra; materialized views (use with care).
  • Consistency: tunable per query; no general cross-partition ACID.
  • Query language: CQL.
  • Scaling: horizontal; also offered as managed (Scylla Cloud).
ClickHouse (columnar / OLAP)
  • Strengths: MergeTree storage, extreme scan/aggregate speed, strong compression, materialized views, high concurrency dashboards.
  • Use cases: product analytics, observability, ad/click streams, real-time BI over append-only facts.
  • Indexing: sparse primary index + data skipping indexes; projections; recent vector similarity support for hybrid analytics.
  • Consistency: eventual across replicas; mutations are heavier than append inserts.
  • Query language: SQL dialect with OLAP functions.
  • Scaling: sharded clusters; ClickHouse Cloud managed option; Kafka ingest common.
DuckDB (columnar / embedded OLAP)
  • Strengths: in-process columnar engine (1.0+ stable), Parquet/Iceberg/Delta reads, vectorized execution, zero server ops.
  • Use cases: notebooks, local ETL, feature engineering, serverless SQL over object storage, CI analytics.
  • Indexing: zone maps/min-max on column parts; not a primary-key OLTP index model.
  • Consistency: single-writer embedded semantics; MotherDuck adds cloud isolation.
  • Query language: ANSI SQL (Postgres-friendly).
  • Scaling: single-node embedded; cloud via MotherDuck for multi-tenant SaaS patterns.
Snowflake-class warehouses (columnar cloud OLAP)

Representative engines: Snowflake, Google BigQuery, Amazon Redshift, Databricks SQL. Same family: separated storage/compute, ANSI-ish SQL, governance-first—not millisecond OLTP.

  • Strengths: elastic warehouses, RBAC, sharing/marketplaces, petabyte scans without owning clusters.
  • Use cases: enterprise BI, compliance reporting, curated lakehouse marts, batch exploration.
  • Indexing: automatic micro-partitions/clustering (vendor-specific); Iceberg tables increasingly portable across engines.
  • Consistency: snapshot isolation for queries; not for interactive row updates.
  • Query language: SQL (dialect per vendor).
  • Scaling: spin warehouses/clusters up/down; cost tied to scanned data and compute time.
pgvector (vector on PostgreSQL)
  • Strengths: vectors beside relational rows—JOINs, transactions, RLS; HNSW/IVFFlat indexes; managed on Supabase/Neon/RDS.
  • Use cases: RAG under ~10–30M vectors, apps already on Postgres, hybrid SQL + similarity.
  • Indexing: HNSW (recall/latency tradeoff), IVFFlat; SQL filters on metadata columns.
  • Consistency: inherits Postgres ACID per transaction.
  • Query language: SQL with <-> / cosine / inner-product operators.
  • Scaling: vertical + read replicas; very large corpora often move to dedicated vector stores or Citus sharding.
Qdrant (dedicated vector)
  • Strengths: Rust core, strong pre-filtered ANN, payload indexes, hybrid dense/sparse, cost-efficient self-host.
  • Use cases: self-hosted RAG at 10M–500M scale, multi-tenant SaaS with rich metadata filters.
  • Indexing: HNSW + quantization (scalar/product/binary).
  • Consistency: collection-level; not a general OLTP system.
  • Query language: REST/gRPC API; filter DSL on payloads.
  • Scaling: sharded clusters; Qdrant Cloud managed.
Pinecone (managed vector)
  • Strengths: fully managed, serverless billing, namespaces, metadata filters, enterprise compliance (SOC2/HIPAA tiers).
  • Use cases: teams wanting zero vector ops, fast PoCs, uneven query traffic on serverless pricing.
  • Indexing: proprietary graph/DiskANN-style (managed tuning).
  • Consistency: eventually consistent replicas; post-filtering can affect result counts under tight filters.
  • Query language: HTTP/SDK upsert/query API.
  • Scaling: opaque horizontal scale; no self-hosted option for regulated on-prem.
Weaviate (vector + hybrid search)
  • Strengths: native BM25 + vector hybrid, schema/classes, modular backends, knowledge-graph patterns.
  • Use cases: semantic search with structured schema, multi-tenant collections, GraphRAG-style retrieval.
  • Indexing: HNSW; inverted index for BM25; optional generative modules.
  • Consistency: class/shard level; schema migrations need planning.
  • Query language: GraphQL API + REST; hybrid queries first-class.
  • Scaling: K8s/Helm; Weaviate Cloud; manual shard rebalance in self-host.
Milvus (vector at scale)
  • Strengths: distributed architecture, multiple ANN types (HNSW, IVF-PQ, DiskANN), GPU index builds, Milvus Lite for dev.
  • Use cases: 100M–billions of vectors, recommendation catalogs, frequent large index rebuilds.
  • Indexing: pluggable index types + quantization; pre-filter support.
  • Consistency: eventually consistent segments; higher ops surface (coordinator/query/data nodes).
  • Query language: SDK/ORM; SQL-like interfaces in ecosystem tools.
  • Scaling: horizontal sharding default; Zilliz Cloud managed.
Neo4j (property graph)
  • Strengths: native graph storage (index-free adjacency), Cypher, graph algorithms, Bloom visualization.
  • Use cases: fraud rings, recommendations, knowledge graphs, dependency/impact analysis, identity graphs.
  • Indexing: label/property indexes for entry points; traversals follow stored relationships.
  • Consistency: ACID on core edition; cluster for HA (fabric/sharding patterns vary by edition).
  • Query language: Cypher (open spec); GQL momentum in standards.
  • Scaling: scale-up + read replicas common; very large graphs need modeling/partition strategies.
TimescaleDB (time-series on PostgreSQL)
  • Strengths: hypertables (auto time partitioning), compression, continuous aggregates, full SQL + joins to relational data.
  • Use cases: metrics, IoT, finance ticks when Postgres ops and SQL matter more than pure ingest records/sec.
  • Indexing: time + tag indexes on chunks; retention policies.
  • Consistency: Postgres ACID.
  • Query language: SQL + time_bucket helpers.
  • Scaling: vertical; multi-node Timescale for distributed chunks where licensed/deployed.
InfluxDB (purpose-built time-series)
  • Strengths: line-protocol ingest, retention/downsampling, Flux (and SQL in InfluxDB 3 lineage) for analytics.
  • Use cases: DevOps metrics, IoT telemetry, high-cardinality monitoring pipelines.
  • Indexing: series key (measurement + tags); TSM/engine optimized for time ranges.
  • Consistency: per-point writes; not cross-series transactions.
  • Query language: Flux; SQL interface in newer cloud/core offerings.
  • Scaling: InfluxDB Cloud/server clusters; 3.x columnar object-store direction for analytics scale.
Embedded & edge (SQLite, DuckDB, libSQL)
  • Strengths: no network hop, ship data with the app, deterministic tests, WASM/mobile targets (SQLite/libSQL).
  • Use cases: offline clients, edge analytics on Parquet, CLI tools, embedded agents, local-first sync (CRDT + SQLite).
  • Indexing: SQLite B-tree OLTP; DuckDB column statistics for analytics—not interchangeable roles.
  • Consistency: single-file or in-process; replication via app logic or sync products (Litestream, Turso/libSQL).
  • Query language: SQL on both; pick SQLite for mutable OLTP rows, DuckDB for analytical scans.
  • Scaling: scale-out happens at the app tier (many embedded DBs), not inside one file.
CockroachDB (distributed SQL / NewSQL)
  • Strengths: Postgres-compatible wire protocol, serializable default isolation, survivable regions, row-level locality controls.
  • Use cases: global OLTP needing horizontal scale without manual sharding, multi-cloud/Kubernetes deployments.
  • Indexing: distributed B-tree indexes maintained cluster-wide.
  • Consistency: serializable transactions across ranges (Raft per range).
  • Query language: PostgreSQL-compatible SQL (check feature parity for exotic types).
  • Scaling: add nodes; automatic rebalancing; CockroachDB Cloud managed.
Google Cloud Spanner (distributed SQL class)
  • Strengths: globally distributed SQL, external consistency via TrueTime, managed ops, strong multi-region HA story on GCP.
  • Use cases: financial ledgers, global inventory, regulated workloads already on GCP needing strict ordering.
  • Indexing: secondary indexes (async backfill awareness); interleaved tables for locality.
  • Consistency: externally consistent reads/writes; TrueTime-bound staleness controls.
  • Query language: Spanner SQL (PostgreSQL dialect compatibility expanding—verify for migrations).
  • Scaling: transparent splits; GCP-only service (compare YugabyteDB/TiDB for portable Spanner-like models).
Also in NewSQL (YugabyteDB, TiDB)
  • YugabyteDB: Postgres-compatible API, DocDB storage, multi-cloud; Spanner-inspired replication.
  • TiDB: MySQL-compatible wire protocol, TiKV row store, HTAP with TiFlash columnar replicas—popular in MySQL ecosystems needing scale.
  • When to evaluate: need distributed SQL but want MySQL (TiDB) or Postgres (Yugabyte) dialect fidelity vs Cockroach/Spanner defaults.
