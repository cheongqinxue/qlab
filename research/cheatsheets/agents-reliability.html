Agents — reliability & ops

Issue vs tool

The issue is operational failure: infinite loops, hung tools, provider outages, context overflow, spend spikes. Tools include timeouts, step caps, circuit breakers, fallbacks, and tracing — often called “guardrails” in vendor docs, but the underlying issue is reliability and operability of agent features.

Bounds & backpressure
Per-request limits
  • Wall-clock timeout (request + per tool).
  • Max agent steps — stop ReAct loops.
  • Token / cost cap per session or tenant.
  • Concurrency queues and 429 when saturated.
Rate limiting & fairness

Per user, tenant, and global limits on LLM and expensive tools so one customer cannot exhaust shared capacity. Layered edge → BFF → model → tool policy → GenAI rate limits.

Degradation & fallbacks
Graceful paths
  • Fallback model or cached FAQ when primary fails.
  • Feature flag: disable agent mode, keep simple RAG+LLM.
  • Partial success (show retrieval if generation fails).
  • Read vs write retry policy — detailed in harness hardening.
Circuit breakers

Fail fast when a dependency error rate spikes; probe with canaries before full restore.

Harness hardening (orchestration layer)
What the harness is responsible for

The harness is your application code around the model: the HTTP or WebSocket handler, the agent graph runner, tool dispatch, auth token forwarding, deadlines, and persistence. It is not the LLM server (vLLM/Ray) and not the payments database. When an interview asks how you prevent duplicate refunds, the harness answer is about when you call tools, what you retry, and what identifiers you attach — assuming downstream APIs and databases also enforce invariants.

Tool taxonomy: read, write, compensate

Register every tool with a class so retry and approval policy is data-driven, not implied by the model prompt. Read tools (search, get_order, list policies) may be retried on timeout or 503 if they do not mutate state. Write tools (create ticket, issue_refund, cancel shipment) must not be blindly retried; they require an idempotency key and often human confirmation in the graph. Compensate tools undo or adjust a prior write (reverse refund, release hold); treat them like writes with their own keys and audit trail.

The model never sees raw HTTP retry configuration. The harness intercepts each tool invocation, looks up the class, and applies the matrix below before the HTTP client runs.

Retry matrix (harness policy)
Tool class On timeout / 503 On 409 / conflict Notes
Read Retry with backoff + jitter (bounded total wait) Return observation to model; do not retry blindly Total wait must stay under user-facing deadline
Write Do not retry same payload; call status/read tool or GET by idempotency key Treat as success if idempotency replay; else surface to user Never “retry whole agent turn” because LLM call failed after write
LLM step Retry generation only if no write ran in same step N/A Re-entrant graph nodes must be safe on replay — see checkpoints

A common production bug is configuring tenacity or a global HTTP retry on the tool client. That duplicates writes when the server actually processed the request but the response was lost. Writes get at most one automatic follow-up: a status read using the same idempotency key or resource id.

Trace id vs idempotency key

A trace id (OpenTelemetry, Langfuse) correlates logs and spans for one user request; every retry may share it. An idempotency key identifies one logical business action (“refund for order X after user confirm at T”) and must be stable across retries of that action. Generate the idempotency key in the harness when the user confirms or when the graph enters an approved write node — store it in graph state and the checkpointer before calling the write tool. Send it as Idempotency-Key (or your API’s equivalent) on every attempt for that action. Do not reuse one key across different user intents or different orders.

Checkpoints, resume, and graph replay

LangGraph-style checkpointers and Temporal-style workflows persist thread state so a process crash can resume. On resume, framework code may re-execute nodes from the last checkpoint forward. Any node that calls a write tool must either be idempotent (same key → no double effect) or split into “plan” (pure) and “execute write” (guarded by key + DB). Human-in-the-loop interrupts should persist pending action + idempotency key; after approval, only the execute node runs.

Pattern for money paths: propose_refund (read-only preview) → interrupt for approval → execute_refund (single write with key from state). If execute_refund times out, the harness runs get_refund_status(order_id, idempotency_key) before trying again.

Deadlines, cancellation, and partial failure

Set a wall-clock deadline on the outer user request and a shorter per-tool timeout so the harness can return a controlled message before the client disconnects. When the user closes the tab, propagate cancellation to in-flight tool HTTP calls where the client library supports it so work does not continue unnoticed. If retrieval succeeded but generation failed, prefer partial UX (show sources, offer human handoff) over silently retrying the entire pipeline including any write steps.

Layering with queues and databases

Duplicate work can arrive because the harness retried, because two API replicas both handled the same message, or because a queue delivered twice. The harness must not assume exactly-once messaging. It should attach idempotency keys to writes; message consumers should dedupe by message id; databases should enforce unique constraints on keys — three separate topics. Queue semantics and transactional idempotency patterns are not expanded on this page.

Python agent stacks often combine: FastAPI + tenacity + Redis limits + Langfuse (or OTel) + LangGraph or Temporal for long runs. Node: similar with BullMQ and Langfuse SDK.

Minimal prod stack (example)
  1. Edge — nginx/Kong rate limit + request timeout.
  2. App — step cap in agent loop; httpx timeout per tool; tenacity on read-only tools.
  3. Observe — OpenTelemetry or Langfuse; export step count and model id.
  4. Control — Unleash flag to fall back to single-shot RAG; LiteLLM or router for model fallback.
What to avoid
  • Retrying mutating tool calls without idempotency keys.
  • Logging full prompts to a third party when contract forbids it — self-host Phoenix/Langfuse or OTel only.
  • Circuit breaker on the whole app because one optional tool fails — scope breakers per dependency.
