How to troubleshoot ML & deep learning

Start here

Describe the symptom in plain language, such as “loss became NaN at step 400,” instead of jumping to fixes. Reproduce the run on a fixed seed, plot training and validation on the same chart, and compare against a run you trust. Change one setting at a time and write down what you changed, so you know what actually helped.

On a new setup, try to overfit a tiny slice of data (often eight to thirty-two examples) until training loss is almost zero. If the model cannot memorize that slice, the problem is usually labels, masking, the data loader, or frozen weights — not a missing schedule tweak.

Train vs validation — four boxes
Train Val Likely issue Read
Bad Bad The model is underfitting, or the pipeline, labels, or learning rate is wrong. generalization, loop, data
Good Bad The model is overfitting, or validation does not match real use (including leakage). generalization, splits
NaN / spike — Training became unstable (exploding gradients, Adam spikes, missing warmup). failure modes
Good Good Offline metrics look fine but production fails — wrong eval metric or a deploy mismatch. metrics, serving
By symptom
Loss is NaN or Inf

Lower the learning rate, add a linear warmup, and clip gradient norm before the optimizer step. Check that Adam’s epsilon is not absurdly small and that mixed-precision scaling is not stuck at a bad value. Inspect one batch for mis-set labels, wrong dtypes, or a loss mask that ignores every token.

See gradient explosion and Adam instability.

Loss flat from step 0

Confirm labels are tied to the right logits (causal shift for language models, padding masked out). Verify the optimizer is updating the parameters you expect and that those tensors require gradients. A flat loss can also mean vanishing gradients in a deep stack, or a rare class that never appears in small batches.

Train improves, val flat or worsens

This pattern usually means overfitting or a validation set that does not reflect deployment. Try stronger regularization, early stopping, more data, or a smaller model, and re-check that users or documents are not split across train and val.

Val better than train

Dropout and augmentation on training only often make validation look slightly better than training, and that is normal. If the gap is large without those effects, treat validation as suspect and look for leakage or an eval set that is too easy.

Out of memory

Use a smaller microbatch and accumulate gradients over several steps so the effective batch size stays the same. Shorten sequences, enable gradient checkpointing, or use a smaller model during development. At inference, reduce context length or use a supported quant format — see training loop and compression.

Training slow but stable

Profile data loading and GPU utilization before changing the math. More DataLoader workers, pinned memory, and mixed precision often help when the loop is I/O or compute bound.

LLM & fine-tune specifics
SFT loss down, chat still bad

Check that you train only on assistant tokens and that demonstrations match how users will prompt the model. Training loss is not chat quality — run a fixed golden prompt list every checkpoint. If the base model is weak on the task, more epochs on thin data will not fix it without better examples or a different stage (eval metrics in metrics).

RL reward up, gibberish or repetition

The reward model may be rewarding length or format instead of usefulness, or KL to the reference model may be too weak. Falling policy entropy with flat human quality is a sign of mode collapse — see mode collapse and PPO.

RAG works in notebook, fails in prod

Align chunking, embedding model, index version, and top-k with production. Good retrieval with bad answers is a grounding problem; good answers with wrong tenant data is an access-control problem — see grounding and security.

Quantized model much worse

Confirm the served runtime matches the quant recipe (GPTQ, AWQ, GGUF, and group size must pair with the loader). Evaluate tasks and long context, not perplexity alone — compression.

Debug moves (low cost)
Sanity checks

Overfit a handful of examples until training loss nears zero; failure here points to a pipeline bug. Sweep a few learning rates on a small subset and confirm validation moves within a short run. Train once with shuffled labels; validation should fall toward chance. If it still improves, look for leakage or a broken loss.

What to log every run

Log training and validation loss, your primary eval metric, gradient norm, learning rate, and throughput. For RL, add reward, KL to reference, and policy entropy. Record git commit, data version, and config so you can compare step ten thousand to a known baseline.

Which sheet to open next

Use failure modes when loss spikes or goes NaN. Use generalization and data for training when training is stable but validation lags. Use training loop and optimizers when you are tuning batch size, warmup, or schedules. Use metrics when you are unsure what “good” should mean. Use serving and reliability when problems appear only after deployment. Use cloud deep learning when the issue is cost, spot preemption, or missing logs on a VM.
