Testing — ML & LLM systems

Two layers

Software tests prove the training and serving code runs correctly (shapes, APIs, no crashes). Model eval proves the model meets quality bars on held-out data — different objective, often slower. You need both; neither replaces the other.

Data tests (before training)
  • Schema and types — columns exist, dtypes match, image paths resolve.
  • Distribution checks — class balance, null rates, out-of-range values (see training data).
  • Leakage — same patient, session, or near-duplicate in train and val splits.
  • Reproducibility — fixed seed produces identical batch order for a tiny shard.

Run data tests in CI when the dataset version changes, not only on laptop.

Training smoke tests

One-batch or one-epoch overfit on a tiny subset: loss should drop sharply if the loop, labels, and loss are wired correctly. Keep runtime under a few minutes in CI — downsample data and model width for the smoke job only. Full training belongs outside PR gates; promotion uses registry and eval (registry).

Eval as regression (golden set)

Freeze a golden evaluation set with known labels or reference answers. On each model candidate, compute metrics defined on metrics; fail CI if below thresholds or if metrics drop more than a tolerance vs the baseline. Store predictions as artifacts when you need to debug a regression.

Serving and inference tests
  • Contract test — POST /predict returns JSON schema, latency under a local budget.
  • Golden vectors — fixed input tensor or image → expected class or embedding within tolerance.
  • Batch vs single — same result for one item run alone vs in a batch when the API promises that.
  • Version header — response includes model id or sha for traceability.
RAG-specific checks

Retrieval regression — fixed queries; assert expected doc ids appear in top-k (does not need an LLM). End-to-end RAG eval — optional LLM judge or human rubric on a small set; run less often than retrieval tests. Grounding policy and hallucination risks → grounding.

LLM non-determinism
  • Pin temperature=0 and seed where the API allows it for repeatable CI.
  • Assert structure — valid JSON, required keys, regex for ids — not exact marketing copy.
  • Separate tool-call tests (mock LLM) from quality eval (live or larger model, nightly).
  • Snapshot LLM outputs only with team agreement and frequent review of diffs.
Agents

Unit-test tool schemas, permission checks, and retry logic with mocked tools. Recorded trajectories (fixture JSON) replay tool sequences without calling the network. Reliability patterns — timeouts, fallbacks — on agents reliability.

What not to duplicate here

Pipeline stage layout, artifact promotion, and prod drift monitoring stay on MLOps pipelines and monitoring. This page is the testing mindset; those pages are the operational wiring.

Chooser

Changed dataloader code → data tests + one-batch smoke. New checkpoint → golden eval + serving golden vector. Changed prompt template → structured output tests + small golden Q&A eval. Changed retrieval index → fixed-query hit test before any LLM eval.
