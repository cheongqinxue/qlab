Cloud deep learning

What this sheet covers

Running training on a cloud GPU is not “rent a box and SSH.” You pay for compute hours, attached disks, object storage, and especially network egress when data crosses regions or leaves Google’s network. This page focuses on cost control, logging, spot (preemptible) survival, and launch discipline — with Google Cloud Platform (GCP) as the concrete example where it helps.

1 — Cost control
Pick the right machine

Match GPU memory to model and batch (7B fine-tune vs 70B full fine-tune are different SKUs). A larger GPU than you need wastes money; too small GPU forces tiny batches and long wall-clock time. For development, use a single smaller GPU or even CPU to validate the pipeline; scale up only after one-batch overfit works (troubleshooting).

On GCP, Spot VMs (formerly preemptible) trade a large discount for the risk that Google stops your VM with short notice. They fit long training jobs that checkpoint and resume, not jobs you cannot restart.

Spot vs on-demand (when each fits)
  • Spot — multi-hour pretrain, fine-tunes with frequent checkpoints to durable storage; you accept occasional restarts.
  • On-demand / committed — short deadline jobs, interactive debugging, or workloads you cannot resume cleanly.

Spot price varies by zone and supply; if preemptions cluster in one zone, try another region or a slightly different machine type.

Data egress on GCP (GCS example)

Cloud Storage (GCS) bills storage per GB-month plus egress when bytes leave a bucket in ways that count as network transfer. Reading training data from GCS into a Compute Engine VM in the same region as the bucket is the cheap pattern: traffic stays on Google’s network and you avoid shipping checkpoints across regions every hour.

Costs bite when you (a) read GCS from VMs in another region, (b) download large datasets to your laptop repeatedly, or (c) serve artifacts to the public internet without a CDN or careful caching. Put the bucket, the VM, and (if used) Vertex/custom training jobs in one region you choose deliberately (e.g. us-central1 VM + us-central1 bucket).

  • Checkpoint to gs://your-bucket/... in the same region as the trainer, not to local boot disk only (boot disk dies with the VM).
  • Upload code and small configs via git or a small image; avoid re-copying multi-TB shards on every job start if a persistent regional bucket already holds them.
  • For multi-cloud or hybrid, assume egress line items will appear — design once, measure in billing reports.
Reading GCP billing

Open Billing in Google Cloud Console (link from the project picker → Billing → Reports / Cost table). Filter by project, time range, and service (Compute Engine, Storage, Networking).

  • Compute Engine — VM hours, attached GPUs, sustained use vs spot line items.
  • Cloud Storage — storage GB-month; egress SKUs often appear under Storage or Network depending on operation.
  • Network — egress to internet, cross-region, or specialty paths — often the surprise after a sweep that copies data wrong.

Use labels on VMs and buckets (team=ml, experiment=bert-finetune) so Cost breakdown → Group by label shows who spent what. Set a budget alert (Billing → Budgets) so email fires at 50% / 90% of monthly cap — alerts do not stop spend, but they prevent month-end shock.

2 — Observability
What to track (training health)

Log the same signals you would use on a local machine, but assume nobody is watching the terminal. At minimum: training and validation loss, your primary eval metric (metrics), learning rate, global step, and throughput (samples or tokens per second).

  • Optimization — grad norm, clip frequency, loss spikes (ties to failure modes).
  • System — GPU utilization, GPU memory used, DataLoader stall time; low util often means CPU bottleneck or small batches.
  • LLM / RL — reward, KL, policy entropy when applicable.
  • Reproducibility — git commit, command line, config file, data snapshot id as run metadata.
Weights & Biases (W&B)

W&B is a common choice: log scalars from your training loop, upload config, compare runs in a dashboard, and optionally store artifacts (checkpoints, plots). Initialize once per process in distributed training (rank 0 only) so you do not duplicate runs.

Treat W&B as the experiment record: name runs clearly, use tags and groups for sweeps, and log hardware (GPU type, spot vs on-demand) so you can relate cost to curves. You can run offline sync if the cluster has intermittent egress; qlab’s local W&B file viewer (BEV) is optional for inspecting run-*.wandb without the cloud UI.

3 — Spot preemption: recover cleanly
What preemption means

GCP Spot VMs can receive a stop signal (often on the order of seconds to a minute). Your process is killed; local disk on the VM is not a durable checkpoint store. Design training so losing the VM loses at most the work since the last successful checkpoint write.

Recovery pattern
  1. Every N minutes or M steps, write checkpoint + optimizer state to GCS in the same region.
  2. On startup, parse gs://... for latest checkpoint (or use a small “pointer” file latest.txt updated atomically).
  3. Restore model, optimizer, scheduler, and global step so learning rate schedule continues correctly.
  4. Handle SIGTERM in your script: trap signal, flush one emergency checkpoint, then exit (best-effort; do not rely on this alone).
  5. Relaunch the VM (manually, via script, or orchestrator) with the same image and startup command that resumes from GCS.

Test recovery once on purpose: kill the VM mid-run and confirm the next launch continues from the expected step without duplicating data epochs.

4 — SkyPilot orchestration
Why SkyPilot

SkyPilot is an open-source layer that turns a YAML task definition into “provision cloud resources, run command, sync artifacts, tear down or autostop.” It helps when you outgrow hand-rolled scripts but do not want a full Kubernetes cluster for every experiment.

  • Declare resources (e.g. one A100, spot allowed) and file mounts (code, data from cloud bucket).
  • Spot-friendly workflows: SkyPilot can retry on preemption in another zone or relaunch according to policy — still requires your job to checkpoint.
  • Multi-cloud optional — same task file can target GCP, AWS, etc., with different cost profiles.
  • Use autostop so idle GPUs shut down after your command finishes — forgotten VMs are a common bill leak.

SkyPilot does not replace checkpoint discipline; it reduces toil around provisioning and retries.

5 — Launch discipline (best practice)
Small-scale local testing first

Run a CPU or one small GPU locally (or on a cheap dev VM) until forward, backward, and one optimizer step work. Overfit a tiny batch, then run a short epoch on a subset before launching a multi-day spot job. Fix data paths, dtype, and masking locally — cloud hourly burn makes debugging expensive.

Estimate OOM before the big job

Start with the smallest batch that runs, watch torch.cuda.max_memory_allocated() (or nvidia-smi peak), then scale batch or sequence length. Enable gradient checkpointing and mixed precision in the dry run if you plan to use them in cloud. If a 7B model OOMs at batch 1 on a 24 GB card, no spot policy fixes that — change model size, LoRA (PEFT), accumulation, or SKU.

Hyperparameter sweeps without idle GPUs

GPUs sit idle while the CPU tokenizes, resizes images, or builds tar shards. Pre-transform upfront: write cached tokenized tensors, LMDB, WebDataset shards, or embedding caches to GCS once, then point sweep jobs at that path. Launch workers only when data is warm; use W&B Sweep or parallel SkyPilot tasks with a shared artifact path.

Label runs like you label invoices

Name runs so future-you knows what they were: llama3-8b-sft-lr3e-5-spot-us-central1, not run-47. Use consistent tags (project, dataset version, spot/on-demand) and GCP resource labels on VMs and buckets so billing reports align with W&B groups.

Chooser
  • Bill shock after one week → Billing → group by service/label; check egress and forgotten VMs.
  • Spot job lost hours → checkpoint interval too long or checkpoints only on local disk.
  • GPU util 30% → dataloader or preprocessing; pre-cache before sweep.
  • Many manual SSH sessions → consider SkyPilot or a thin wrapper script with resume from GCS.
