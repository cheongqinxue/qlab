Ray Serve + vLLM (production)

Split responsibilities

vLLM — loads weights, continuous batching, PagedAttention, OpenAI-compatible HTTP/gRPC; one process (or TP group) per model replica. Ray Serve — deployment graph, autoscaling replicas, request routing, queuing at the Python layer, colocating embed/classifier CPU workers with GPU LLM workers. Pattern: FastAPI/LangGraph BFF → Ray Serve deployment → vLLM replica(s), not “Ray replaces vLLM.”

vLLM — minimal setup
OpenAI-compatible server (reference) 
python -m vllm.entrypoints.openai.api_server \
  --model meta-llama/Llama-3.1-8B-Instruct \
  --dtype auto \
  --max-model-len 8192 \
  --gpu-memory-utilization 0.90 \
  --max-num-seqs 64 \
  --max-num-batched-tokens 8192 \
  --enable-prefix-caching \
  --host 0.0.0.0 --port 8000
  • --gpu-memory-utilization — fraction of GPU RAM for weights+KV; leave headroom if same GPU runs CUDA graphs / NCCL.
  • --max-num-seqs — concurrent sequences (decode slots); raising it ↑ KV RAM, ↑ throughput until memory bound.
  • --max-num-batched-tokens — caps prefill batch; prevents one huge prompt from starving others.
  • TP — add --tensor-parallel-size N when one GPU cannot hold the checkpoint.
Kubernetes (single deployment sketch)
  • One Pod per vLLM replica; request nvidia.com/gpu: 1 (or N for TP — prefer single pod multi-GPU with NCCL).
  • liveness — HTTP /health; readiness — model loaded + optional generate 1 token.
  • preStop — drain: flip readiness false, wait terminationGracePeriodSeconds > longest allowed generation.
  • Mount HF cache PVC or bake image with weights; pin VLLM_VERSION + CUDA driver on node pool.
Queuing & backpressure (vLLM + harness)
Where queues live
Layer Knob Purpose Risk if wrong
API / BFF Global concurrency limit per user Fairness, abuse control Retry storms from clients
Ray Serve max_ongoing_requests, max_queued_requests Reject or 429 when saturated Unbounded queue → memory + tail latency
vLLM max-num-seqs, scheduler queue GPU-side batching Internal pile-up; timeouts cascade
Client harness Deadline per turn, max retries=2, jitter Stop hammering hot GPU Duplicate tool side effects if retrying whole agent turn — harness policy

Rule: cap queue depth at the outermost layer you control (Serve or ingress) so vLLM never holds unbounded waiting requests. Interactive chat: prefer 429 + short message over 60s queue wait. Offline embed jobs: separate deployment with larger batches.

Ray Serve — setup & scaling
Deployment skeleton (Python) 
@serve.deployment(
    autoscaling_config={
        "min_replicas": 1,
        "max_replicas": 6,
        "target_ongoing_requests": 8,
        "upscale_delay_s": 30,
        "downscale_delay_s": 600,
    },
    max_ongoing_requests=10,
    ray_actor_options={"num_gpus": 1},
)
class VLLMDeployment:
    def __init__(self):
        # spawn or connect to vLLM AsyncLLMEngine / HTTP sidecar
        ...

    async def __call__(self, request):
        ...
  • target_ongoing_requests — Ray adds replicas when average in-flight requests per replica exceeds this (after delays).
  • max_ongoing_requests — hard cap per replica; excess should queue at Serve (bounded) or fail fast.
  • min_replicas ≥ 1 for prod chat — scale-to-zero saves $ but cold start (model load) kills SLO.
  • Separate deployments: llm-chat (low batch wait), embed-batch (high batch, CPU/GPU small).
Scaling policy (peak 5× example)
  • Baseline: 1 GPU replica handles ~avg load at target_ongoing_requests=8–16 (measure tokens/s on your model).
  • Peak: max_replicas=6 → 6× capacity if scheduler keeps replicas warm; align with K8s cluster max GPU quota.
  • upscale_delay_s — avoid flapping on 30s spikes; downscale_delay_s — long enough to survive diurnal trough without cold start on next spike.
  • GPU node pool autoscaler must provision nodes before Ray can place new replicas — watch pending pods.
Batching
  • vLLM continuous batching — automatic across concurrent decodes; you tune caps, not manual batch size.
  • Ray Serve batching decorators — use for embedding/classifier microservices, not for token streaming LLM unless offline.
  • Do not route CPU embed and GPU decode through one overloaded actor — split services to prevent embed backlog blocking chat.
Availability & retries
  • Multi-replica + load balancer — Ray Serve handle or K8s Service; sticky sessions not required for stateless LLM if KV is per-request.
  • Idempotent reads — safe to retry HTTP GET/tool reads; mutations (cart, refund ticket) need idempotency keys at app layer.
  • Circuit breaker — if p95 latency > 2× SLO or error rate > 5% for 1 min, stop retries to vLLM; return degraded response or queue to human.
  • Canary — new model revision on 5% traffic; compare error rate, tokens/s, task success before full rollout.
  • Graceful drain — on deploy, stop sending new requests to old revision until in-flight completes (Ray max_ongoing_requests + K8s preStop).
Failure modes (symptoms → diagnose → fix vs prevent)

Fix now (live) — stops the incident while users are still hitting the system (flags, admission, emergency serve deploy, kubectl). After stable / prevent — insurance and hardening once traffic is healthy; not a substitute for live fixes. Channels: BFF flag (Postgres admin UI, LaunchDarkly, or kubectl set env) · serve deploy (YAML in repo) · cloud/K8s UI or CLI (nodes, quota).

Ray UI is for diagnosis (Serve → replica states). Live capacity changes are almost always serve deploy on Git-managed YAML plus BFF flags and kubectl/cloud console for GPUs. Metric meanings and symptom patterns → metrics reference below. See also failure modes and troubleshooting.

Production metrics (vLLM & Ray Serve)
Where to scrape (two layers)

vLLM exposes Prometheus text on its HTTP server (commonly /metrics on the worker port, e.g. 8000). That is where KV block-pool and scheduler counters live. Ray Serve exposes deployment-level queue and replica metrics (Ray metrics agent / Grafana dashboards); it does not show PagedAttention block usage unless you forward vLLM metrics from each replica. In production, scrape every vLLM pod plus the Serve control plane, and join in Grafana on model, replica, and deployment labels. Exact metric names shift between vLLM releases — run curl -s http://<vllm-host>:8000/metrics | rg -i 'cache|preempt|waiting|running' once per upgrade and pin aliases in your dashboard.

KV “pool” — what you can and cannot see

vLLM stores past keys and values in a fixed pool of GPU blocks (PagedAttention), not as one growable buffer per request. There is no standard UI that lists “block 412 of 500.” The engine publishes aggregate fill level (cache usage percentage) and preemption count, which are the operational view of pool stress. nvidia-smi shows total VRAM used (weights + KV + activations) but cannot separate block-pool saturation from weight footprint; do not use GPU util alone as a health signal.

vLLM metrics — what they measure
Metric (typical name) What it measures Symptoms when bad What it usually means
gpu_cache_usage_perc (or vllm:gpu_cache_usage_perc) Fraction of the KV block pool currently allocated to active sequences (0–100%). Sustained high 90s+; TTFT p99 up; new streams slow to first token. Too many concurrent or long contexts for max-num-seqs, gpu-memory-utilization, and model size. Pool is full or near full; scheduler will preempt or reject.
num_preemptions_total (counter, use rate) How often the scheduler evicted a sequence’s KV blocks to free space for others. Counter slope spikes; users see long pauses then slow resume; TTFT variance widens. KV capacity mismatch with load — not “caching broken,” but not enough blocks for everyone at once. Victims pay re-prefill cost later.
num_requests_running Sequences actively executing on GPU (prefill or decode), holding KV blocks. Pinned near max-num-seqs; latency climbs for everyone. Engine at concurrency ceiling; admission or more replicas needed, or lower caps / shorter context.
num_requests_waiting Requests accepted by vLLM but not yet scheduled on GPU (internal scheduler queue). Waiting > 0 for long periods; TTFT includes long queue wait; TPOT may still look normal for lucky running requests. GPU-side backlog — distinct from Ray Serve queue. Fix with fewer arrivals (429 at BFF/Serve), more healthy replicas, or lower per-request work.
prompt_tokens_total / generation_tokens_total Throughput counters for prefill vs decode tokens. Prompt tokens spike without generation growth. Prefill-heavy traffic (long system prompts, RAG dumps) — head-of-line for TTFT; tune chunked prefill / token budgets.
Request latency histograms (if enabled) Engine-reported e2e or stage latency per request class. TTFT bucket shifts right while decode buckets stable. Confirms bottleneck is before steady decode (queue + prefill + preemption), not inter-token generation.
CUDA OOM / restart (logs + kube restartCount) Process-level failure when allocation exceeds VRAM. Intermittent 500s; pod restarts; one bad prompt correlates with crash. Hard limit hit — lower max-model-len, max-num-seqs, or memory fraction; distinct from soft preemption but same family (KV pressure).

Preemption in vLLM means the scheduler freed another sequence’s KV blocks to admit work; that sequence may later recompute prefill to rebuild KV. It is not Kubernetes preempting a pod unless you use spot instances separately.

Ray Serve metrics — what they measure
Metric (typical name) What it measures Symptoms when bad What it usually means
serve_deployment_queued_queries (or queue depth per deployment) HTTP requests waiting at Serve because replicas are at max_ongoing_requests. Queue grows without bound (if uncapped); TTFT rises before vLLM even sees traffic. Python-layer backlog — scale replicas, raise caps cautiously, or 429 at ingress. Check replica count vs GPU quota.
Ongoing / in-flight requests per replica Active calls into the deployment actor (streaming counts until response completes). Every replica at max_ongoing_requests; autoscale not adding ready replicas. All replicas busy — pair with vLLM waiting/running. If Serve low but vLLM high, bottleneck is inside worker; if Serve high and vLLM low, routing or cold workers.
Replica count (desired vs running vs healthy) How many Serve replicas exist and pass health checks. Desired > running; Ray UI shows STARTING/PENDING; latency up without vLLM preemption spike. Pending replica storm or slow model load — not fixable by vLLM tuning alone. See failure table rows for no GPU / pending storm.
Actor restarts / deployment errors Crash loops in Serve wrapper or failed init connecting to vLLM. Error rate spikes; partial availability. Config, OOM in sidecar, or bad deploy — distinct from KV preemption but similar user symptom (503/500).

Application metrics (BFF / harness)

Complement engine metrics with harness spans: time in queue (Serve), time to first token (client-visible), tool latency, and retry count per session. Engine metrics explain the GPU; harness metrics explain whether TTFT grew because of Ray queue, vLLM wait, prefill, or preemption. Align with harness hardening for retry counters.

Observability
Metrics to chart (minimum dashboard)
  • Latency — TTFT, inter-token latency, total generation time (per model revision).
  • vLLM — gpu_cache_usage_perc, preemption rate, num_requests_running/waiting.
  • Ray Serve — queue depth, replica count (desired vs ready), ongoing requests per deployment.
  • Business — tool error rate, escalation rate (Langfuse/LangSmith or OTel).
Tracing

Propagate trace_id from BFF → Ray → vLLM request id. Log not prompts containing PII in prod INFO; sample debug traces. Align with observability sheet.

Lever Typical savings Tradeoff
Right-size model (8B vs 70B) 3–10× $/token Quality on hard tasks; route hard queries up-tier
Quant weights (AWQ/GPTQ/FP8) ~2× throughput same GPU Eval regression on your prompts
min_replicas=1, cap max_replicas Linear in GPU-hours Peak queue during flash sales

Separate batch embed off peak hours Cheaper spot windows Stale index until job completes

Unit economics: estimate $/1M output tokens = (GPU $/hr × replicas) / (tokens/s × 3600 × replicas). Break-even vs OpenAI-class API often near steady 24/7 load on one or more L40S/H100 — bursty support chat may stay hybrid.

Production checklist
  1. Pin vLLM + CUDA + model revision + quant recipe in registry (registry).
  2. Set outer queue + max-num-seqs so worst-case KV fits VRAM (load test with max context agents).
  3. Autoscale on ongoing requests, not CPU — GPU-bound workloads show low CPU until saturated.
  4. Retry policy: bounded, jittered; never blind retry on 503 from saturated vLLM.
  5. Runbooks: GPU OOM → lower max-num-seqs; NCCL hang → restart TP group; model download fail → init container.
