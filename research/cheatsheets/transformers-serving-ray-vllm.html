Production patterns for self-hosted LLM inference. Overview → serving & hosting. Agent SLOs → reliability. KV/VRAM math → efficiency.

Ray Serve + vLLM (production)

Split responsibilities

vLLM — loads weights, continuous batching, PagedAttention, OpenAI-compatible HTTP/gRPC; one process (or TP group) per model replica. Ray Serve — deployment graph, autoscaling replicas, request routing, queuing at the Python layer, colocating embed/classifier CPU workers with GPU LLM workers. Pattern: FastAPI/LangGraph BFF → Ray Serve deployment → vLLM replica(s), not “Ray replaces vLLM.”

vLLM — minimal setup
OpenAI-compatible server (reference) 
python -m vllm.entrypoints.openai.api_server \
  --model meta-llama/Llama-3.1-8B-Instruct \
  --dtype auto \
  --max-model-len 8192 \
  --gpu-memory-utilization 0.90 \
  --max-num-seqs 64 \
  --max-num-batched-tokens 8192 \
  --enable-prefix-caching \
  --host 0.0.0.0 --port 8000
  • --gpu-memory-utilization — fraction of GPU RAM for weights+KV; leave headroom if same GPU runs CUDA graphs / NCCL.
  • --max-num-seqs — concurrent sequences (decode slots); raising it ↑ KV RAM, ↑ throughput until memory bound.
  • --max-num-batched-tokens — caps prefill batch; prevents one huge prompt from starving others.
  • TP — add --tensor-parallel-size N when one GPU cannot hold the checkpoint.
Kubernetes (single deployment sketch)
  • One Pod per vLLM replica; request nvidia.com/gpu: 1 (or N for TP — prefer single pod multi-GPU with NCCL).
  • liveness — HTTP /health; readiness — model loaded + optional generate 1 token.
  • preStop — drain: flip readiness false, wait terminationGracePeriodSeconds > longest allowed generation.
  • Mount HF cache PVC or bake image with weights; pin VLLM_VERSION + CUDA driver on node pool.
Queuing & backpressure (vLLM + harness)
Where queues live
Layer Knob Purpose Risk if wrong
API / BFF Global concurrency limit per user Fairness, abuse control Retry storms from clients
Ray Serve max_ongoing_requests, max_queued_requests Reject or 429 when saturated Unbounded queue → memory + tail latency
vLLM max-num-seqs, scheduler queue GPU-side batching Internal pile-up; timeouts cascade
Client harness Deadline per turn, max retries=2, jitter Stop hammering hot GPU Duplicate tool side effects if retrying whole agent turn

Rule: cap queue depth at the outermost layer you control (Serve or ingress) so vLLM never holds unbounded waiting requests. Interactive chat: prefer 429 + short message over 60s queue wait. Offline embed jobs: separate deployment with larger batches.

Ray Serve — setup & scaling
Deployment skeleton (Python) 
@serve.deployment(
    autoscaling_config={
        "min_replicas": 1,
        "max_replicas": 6,
        "target_ongoing_requests": 8,
        "upscale_delay_s": 30,
        "downscale_delay_s": 600,
    },
    max_ongoing_requests=10,
    ray_actor_options={"num_gpus": 1},
)
class VLLMDeployment:
    def __init__(self):
        # spawn or connect to vLLM AsyncLLMEngine / HTTP sidecar
        ...

    async def __call__(self, request):
        ...
  • target_ongoing_requests — Ray adds replicas when average in-flight requests per replica exceeds this (after delays).
  • max_ongoing_requests — hard cap per replica; excess should queue at Serve (bounded) or fail fast.
  • min_replicas ≥ 1 for prod chat — scale-to-zero saves $ but cold start (model load) kills SLO.
  • Separate deployments: llm-chat (low batch wait), embed-batch (high batch, CPU/GPU small).
Scaling policy (peak 5× example)
  • Baseline: 1 GPU replica handles ~avg load at target_ongoing_requests=8–16 (measure tokens/s on your model).
  • Peak: max_replicas=6 → 6× capacity if scheduler keeps replicas warm; align with K8s cluster max GPU quota.
  • upscale_delay_s — avoid flapping on 30s spikes; downscale_delay_s — long enough to survive diurnal trough without cold start on next spike.
  • GPU node pool autoscaler must provision nodes before Ray can place new replicas — watch pending pods.
Batching
  • vLLM continuous batching — automatic across concurrent decodes; you tune caps, not manual batch size.
  • Ray Serve batching decorators — use for embedding/classifier microservices, not for token streaming LLM unless offline.
  • Do not route CPU embed and GPU decode through one overloaded actor — split services to prevent embed backlog blocking chat.
Availability & retries
  • Multi-replica + load balancer — Ray Serve handle or K8s Service; sticky sessions not required for stateless LLM if KV is per-request.
  • Idempotent reads — safe to retry HTTP GET/tool reads; mutations (cart, refund ticket) need idempotency keys at app layer.
  • Circuit breaker — if p95 latency > 2× SLO or error rate > 5% for 1 min, stop retries to vLLM; return degraded response or queue to human.
  • Canary — new model revision on 5% traffic; compare error rate, tokens/s, task success before full rollout.
  • Graceful drain — on deploy, stop sending new requests to old revision until in-flight completes (Ray max_ongoing_requests + K8s preStop).
Failure modes (symptoms → diagnose → fix vs prevent)

Fix now (live) — stops the incident while users are still hitting the system (flags, admission, emergency serve deploy, kubectl). After stable / prevent — insurance and hardening once traffic is healthy; not a substitute for live fixes. Channels: BFF flag (Postgres admin UI, LaunchDarkly, or kubectl set env) · serve deploy (YAML in repo) · cloud/K8s UI or CLI (nodes, quota).

Failure Symptoms Diagnose Fix now (live) After stable / prevent
No GPU for new replica p95 latency climbs, 503/429 rise, users report hangs. Serve replica count below max but load stays high. Ray UI → Serve → replicas STARTING/PENDING. kubectl describe pod → insufficient nvidia.com/gpu. Autoscaler events blocked or at max. BFF flag: human-only / no new LLM turns. serve deploy: set non-critical deployment max_replicas: 0 to free a GPU; set chat max_replicas to schedulable GPU count only. K8s/cloud CLI or UI: add one GPU node if pool allows. Do not increase client retries. Raise GPU pool maxCount and quota in IaC. Set max_replicas ≤ proven schedulable GPUs. Alert on Pending worker pods. Document which deployment to drain first.
Pending replica storm Autoscaling keeps adding replicas but healthy capacity never grows. Queue depth and error rate increase together. serve status or Ray UI: desired replicas ↑, ready flat. Many STARTING; kubectl Pending GPU or stuck init. BFF flag: open LLM circuit / admission off. serve deploy: chat max_replicas = number of GPUs you can run now (often 1); scale embed/staging to max_replicas: 0 so a pending chat actor can bind a GPU. Do not keep raising desired replicas. Pre-warm (insurance): raise min_replicas before known peaks so spare models are loaded. Fix root scheduling (pool size, init image). Re-enable higher max_replicas only after each extra GPU is proven schedulable.
Retry storm GPU util high but errors still spike. Edge QPS exceeds real user sessions. vLLM sees duplicate or bursty retries after timeouts. Compare gateway QPS to session count. BFF retry metrics ↑. 503/504 aligned with client retry loops. BFF flag: force circuit open + set max retries to 0. User sees handoff or “try again” — no new vLLM calls. Do not tune Ray autoscale until retry multiplier falls. Ship bounded retries with jitter in BFF code. Idempotency keys on tool mutations. Dashboard alert when retry ratio or LLM QPS/session exceeds threshold.
Slow scale-out (peak missed) Burst overloads system; latency recovers before new replicas become ready. Incidents match campaigns or outages. Time from upscale to ready replica > SLO (node boot + pull + model load). Autoscaler latency in cloud metrics. BFF flag: admission cap or overflow API for the rest of the burst. K8s/cloud UI: manually add GPU nodes if the peak is still ongoing. serve deploy: only raise min_replicas if free GPUs already exist — useless if Pending. Pre-warm: min_replicas + extra nodes before scheduled events. Smaller upscale_delay_s if flapping is acceptable. Load-test cold-start time in runbooks.
Unbounded queue Users wait tens of seconds with no tokens. Serve/worker memory grows. Timeouts cascade. Ray metrics: queue length unbounded. max_queued_requests unset or too high. vLLM num_requests_waiting pegged. BFF flag: reject new streams. serve deploy: lower max_queued_requests; return 429 at Serve. Gateway deadlines on open SSE. Lower max-num-seqs only if OOM — else reject beats pile-up. Set permanent queue caps in serve_config.yaml. Load-test tail latency with cap. User-visible queue position optional.
All replicas saturated Every request slow; cliff to 503 when caps hit. Ongoing per replica ≈ max_ongoing_requests. Per-replica ongoing at cap. KV cache % high. TTFT and inter-token latency both bad. BFF flag: shed load (human queue, smaller model route, overflow API). If GPUs exist but replicas not scaling, check upscale delays — live lever is admission, not “more max” without GPUs. Raise max_replicas with matching GPU pool. Tune target_ongoing_requests. Quant or smaller model for steady-state headroom.
GPU OOM / vLLM crash Intermittent 500s, pod restarts, one long thread kills a worker. CUDA OOM or KV exhausted in logs. Pod restart count ↑. vLLM OOM logs. Often long agent context. BFF flag: truncate or block extreme context on new turns. kubectl: delete one hung worker pod. serve deploy / vLLM args: lower max-num-seqs or max-model-len on surviving replicas. VRAM budget in runbooks. Product max context. KV quant where supported. Regression test on longest agent trace.
Cluster at quota / autoscaler max Pending pods for hours. No new nodes. Quota or pool max in cloud UI. GPU quota 100%. Node pool maxCount hit. Autoscaler “scale-up forbidden”. BFF flag: overflow API + human-only. serve deploy: max_replicas = GPUs you actually have (stop pending storm). Repurpose dev/batch GPU nodes to prod pool if break-glass allows. Quota increase in cloud IaC. Permanent pool headroom. Right-size max_replicas to quota reality.

Ray UI is for diagnosis (Serve → replica states). Live capacity changes are almost always serve deploy on Git-managed YAML plus BFF flags and kubectl/cloud console for GPUs. See failure modes and troubleshooting.

Observability
Metrics to chart
  • TTFT, inter-token latency, total generation time — per model revision.
  • GPU — util %, KV cache usage %, num_requests_running/waiting (vLLM exposes Prometheus).
  • Ray — queue length, replica count, ongoing requests, actor restarts.
  • Business — tool error rate, escalation rate, WF conversion (from Langfuse/LangSmith traces).
Tracing

Propagate trace_id from BFF → Ray → vLLM request id. Log not prompts containing PII in prod INFO; sample debug traces. Align with observability sheet.

Cost control (cloud GPU)
Lever Typical savings Tradeoff
Right-size model (8B vs 70B) 3–10× $/token Quality on hard tasks; route hard queries up-tier
Quant weights (AWQ/GPTQ/FP8) ~2× throughput same GPU Eval regression on your prompts
min_replicas=1, cap max_replicas Linear in GPU-hours Peak queue during flash sales
Spot / preemptible GPU nodes 50–70% off on-demand Need checkpoint restart + ≥2 replicas for chat SLO
Separate batch embed off peak hours Cheaper spot windows Stale index until job completes
API overflow for burst only Cap owned GPU count Data residency, $/M tokens at sustained load

Unit economics: estimate $/1M output tokens = (GPU $/hr × replicas) / (tokens/s × 3600 × replicas). Break-even vs OpenAI-class API often near steady 24/7 load on one or more L40S/H100 — bursty support chat may stay hybrid.

Production checklist
  1. Pin vLLM + CUDA + model revision + quant recipe in registry (registry).
  2. Set outer queue + max-num-seqs so worst-case KV fits VRAM (load test with max context agents).
  3. Autoscale on ongoing requests, not CPU — GPU-bound workloads show low CPU until saturated.
  4. Retry policy: bounded, jittered; never blind retry on 503 from saturated vLLM.
  5. Runbooks: GPU OOM → lower max-num-seqs; NCCL hang → restart TP group; model download fail → init container.
