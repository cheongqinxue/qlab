Chunking & context

The chunk size problem

Retrieval embeds a chunk, not the whole document. If the chunk is too small, the vector loses context (pronouns, section topic) and the right passage may not match the query. If it is too large, the vector averages many ideas and rank drops; the LLM also wastes context on irrelevant text.

There is no single best token count — it depends on doc type, embed model, and query style. These techniques change where you cut or what you embed.

Too small vs too large (symptoms)
  • Too small — “it” / “the policy above” doesn’t retrieve; answers need two adjacent chunks
  • Too large — right doc, wrong section; retrieval score mediocre; LLM ignores buried sentence
  • Fix direction — add context to embed, retrieve small but read big, or hierarchy/summaries
Baselines (still used)
  • Fixed token window — e.g. 256–512 tokens; simple, reproducible
  • Overlap — repeat 10–20% between windows so boundaries don’t split facts
  • Structure-aware — split on headings, paragraphs, HTML blocks, PDF layout
Retrieve small, feed large
Parent document / sentence window

Index small units for precise vectors; at generation time, expand to a parent paragraph, section, or full page (LlamaIndex “sentence window”, “auto-merge”, classic parent–child retriever).

Search stays sharp; the LLM sees enough surrounding text.

Contextual retrieval (Anthropic, 2024)

Before embedding each chunk, prepend a short context blurb generated by an LLM (e.g. “This chunk is from {doc title}, section {heading}; it discusses …”). Embed context + chunk so the vector carries document-level meaning.

Extra index cost (LLM calls at ingest); often paired with reranking.

Embed with more context first
Late chunking (2024)

With a long-context embedding model, run the transformer over the full document (or long span) once, then pool token vectors into chunk embeddings — chunks inherit cross-chunk context in the representation. Contrasts with “early” chunk-then-embed, where each chunk is encoded in isolation.

Paper line: “Late Chunking” — contextual chunk embeddings using long-context encoders. Needs compatible embed API/model.

Semantic / topic splits

Break where embedding similarity between adjacent sentences drops (clustering, binary search on boundaries), instead of fixed token counts. Adapts to dense vs sparse sections.

Hierarchy & multi-level indexes
RAPTOR (tree summaries)

RAPTOR — recursively cluster chunks, summarize clusters, embed summaries, build a tree. Query can hit leaf chunks or higher summary nodes — helps questions that need whole-document gist plus detail.

Proposition-level indexing

Use an LLM to split text into atomic propositions (standalone facts), embed those. Good when answers are single facts; risk of over-splitting narrative flow.

Related: proposition-centric retrieval research (factoid QA); not identical to fixed-size chunks.

Hierarchy sketch

Query may retrieve a leaf, a section summary, or both (RAPTOR-style / multi-vector collections).

Different axis — not chunk size but interaction
Late interaction (ColBERT-style)

Store token-level embeddings per doc; score query tokens against doc tokens at retrieval time. Avoids one vector per chunk averaging everything. Heavier index; different trade-off than “bigger chunks.”

Agentic / LLM-chosen boundaries

Model proposes split points or merges chunks dynamically per query. Flexible but costly and less deterministic; use when corpus is messy and offline rules fail.

How to choose (practical)
  • Start: structure-aware + overlap; measure recall@k on real questions
  • Still missing context in vectors → contextual retrieval or late chunking (if model supports it)
  • Retrieval hits but LLM lacks surround → parent doc / sentence window
  • Whole-doc questions → RAPTOR or summary index + leaf index (hybrid query)
  • Re-chunking requires re-embed; version the index with chunk strategy id
