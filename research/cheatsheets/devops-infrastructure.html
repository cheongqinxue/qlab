DevOps — infrastructure

Infrastructure as code (IaC)

Infrastructure as Code means servers, networks, databases, and IAM bindings are defined in files (Terraform, Pulumi, CloudFormation, Bicep) stored in git. You review infra changes like code changes, reproduce environments, and avoid “clickops” nobody can replay.

Twelve-factor habits (apps)
  • Config in environment — database URLs and feature flags via env vars, not hardcoded.
  • Secrets outside git — Secret Manager, Vault, or CI secret store; see repo .env-template pattern.
  • Stateless processes — store uploads in object storage, sessions in Redis, not local disk on one pod.
  • Logs as streams — app writes stdout; platform collects (observability).
  • Dev/prod parity — same container image from staging to prod; only config changes.
Cloud building blocks
Compute

VMs, autoscaling groups, Kubernetes node pools, or serverless containers. Pick based on control vs ops load. GPU workloads often stay on VMs or specialized pools — cloud DL.

Networking (head start)

Load balancer terminates TLS and spreads HTTP to healthy backends. VPC isolates private subnets; only public edges expose ports. Understand ingress vs internal service before debugging “connection refused.”

Data stores

Managed Postgres, Redis, object storage — provisioned via IaC with backups and encryption at rest enabled by default in prod. Picking DB types → databases.

Terraform mental model

You declare resources (bucket, VM, IAM role); Terraform plans a diff and applies it. State tracks what exists — store remote state (S3/GCS + lock) for teams. Modules reuse patterns (e.g. “standard web service”). Start small: one project, one environment, then split staging/prod workspaces.

Chooser

Solo demo → PaaS + manual env vars may skip Terraform for months. Shared staging/prod → IaC for databases, buckets, and IAM from day one. Regulated → separate accounts/projects, audit logs, no shared prod credentials on laptops.
