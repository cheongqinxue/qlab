GenAI rate limits & traffic layers

Why layers matter

A logged-in support chatbot can be abused by scripts, by retry storms, or by one user opening many streams that exhaust GPU and tools. A single global rate limit is not enough: the edge must protect login and static assets, the BFF must enforce per-user fairness and agent policy, the model tier must cap tokens and concurrency, and tools must limit irreversible actions. Each layer uses cheap signals before the next layer pays for LLM inference.

The four layers
Layer What hits it first Typical controls Identity key
Edge (CDN, LB, API gateway) Browser loading UI, TLS, unauthenticated probes Conn rate per IP, WAF, geo rules, TLS-only, bot scores IP, optional device fingerprint
Auth (IdP or login API) Password, OTP, SSO callbacks Fixed retries per account per 24h; lockout; CAPTCHA after N fails Account id + IP
BFF (app + agent harness) Chat SSE/WebSocket, agent turns after login Per-user short + long windows; max concurrent streams; coalesce bursts; step/token caps User id from verified JWT
Model serve (Ray/vLLM/API) LLM inference requests from BFF Tenant token/min; max batch queue; 429 when saturated Service account + tenant id
Tools (email, refund, search) Side-effecting HTTP from harness Per-tool rate; mutating stricter than read; HITL on money paths User id + tool name

Edge is the first infrastructure hop (Cloudflare, nginx, Kong, ALB)—not your LangGraph process. After login, chat limits belong on the BFF, not only on IP, or one NAT office shares one bucket.

Limit types (combine several)
Short vs long windows

A short window (e.g. per minute) allows legitimate bursts—user pastes order history—while blocking machine-gun clicks. A long window (e.g. per day) stops sustained abuse even if each minute stays under the short cap. Set short loose enough for UX; set long tight enough that repeated bursts cannot continue indefinitely.

Concurrency caps

Limit open chat streams per user (often 1–2) so one account cannot hold many GPU-backed sessions. Concurrency limits beat request-per-minute alone for agent workloads where one “request” runs fifty LLM steps.

Token and cost budgets

Per session or per day input+output token ceilings stop runaway agent loops from draining budget. Enforce in the harness before calling the model; decrement on each completion; hard-stop with a user-visible message when exhausted.

Burst coalescing

UI debounce and BFF single-flight per thread (or merge rapid messages into one agent run) prevent one paste from becoming ten parallel agent jobs. That is a product/control choice, not only a higher rate limit.

Responses: 429, queue, degrade

429 Too Many Requests with Retry-After is appropriate at edge and BFF when you want clients to stop immediately—pair with harness rules that do not retry aggressively on 429. A small bounded queue at BFF can smooth spikes; an unbounded queue before GPU causes tail latency and retry storms. Under extreme load, feature-flag degrade (FAQ-only, no agent, human queue) protects the model tier — see failure runbooks.

Metrics and alerts
  • 429 rate by layer (edge vs BFF vs vLLM) — identifies where pressure appears.
  • Auth failures per account and IP — brute-force signal.
  • Concurrent streams per user — abuse or client bug.
  • Tokens per user per day — cost and agent-loop abuse.
  • Tool calls per user per tool — especially mutating tools.
  • LLM QPS ÷ active sessions — retry storm multiplier (harness).
Example policy sketch (support chat, logged-in)

Edge: connection rate per IP for anonymous routes. Auth: 7 failed logins per account per 24h. BFF: max 2 concurrent streams per user; 30 agent turns per minute (short); 500 per day (long); coalesce messages within 300ms on same thread; 100k tokens per day per user. Tools: 10 read calls/min; 3 refund-related calls/hour with HITL above $0. Model: tenant-wide token/min cap with 429 when Ray/vLLM queue exceeds bound. Tune numbers from load test and cost model—this block is a template, not universal constants.
