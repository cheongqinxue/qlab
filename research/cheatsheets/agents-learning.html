Agents — learning & improvement

“Self-learning” is not one thing

People use self-learning agent for anything from “retries with a written critique” to “nightly fine-tune on production logs.” Those differ in what changes (prompt context only vs external memory vs model weights), risk, and who approves. Production teams usually combine verifiers + logging + periodic offline updates, not continuous online weight learning.

Verifiers — gate before you “learn”
Outcome verifiers

Hard checks on the final artifact: unit tests pass, SQL result row count, JSON schema valid, citation span matches source chunk. Without a verifier, “successful” trajectories are noise — you will fine-tune on hallucinated wins.

Process & consistency checks
  • Tool allowlists — reject traces that called exfiltration endpoints.
  • Chain-of-verification (CoVe) — model generates verification questions and answers them before commit; reduces confident errors in logs marked “good.”
  • LLM-as-judge — useful for drafts; weak as sole gate for safety or math — pair with deterministic checks.
Promotion pipeline (memory or weights)

Treat learning like a CI pipeline: episode completes → automated checks → optional human review → write to skill library or queue for training batch. Never promote directly from a single unverified success in a hostile environment (web, user-uploaded docs).

  • Version skills and memory entries; rollback when eval regresses.
  • Hold out a fixed eval set (see below) — same idea as embedding regression gates on representations.
Research patterns (names worth knowing)
Reflexion & critique loops

Failed episode → natural-language critique → next attempt sees critique in context. Learning is within-task only unless you persist critiques to episodic memory for similar future goals.

Voyager-style skill acquisition

Agent explores an environment (e.g. Minecraft APIs), proposes code skills, keeps those that pass environment feedback. Outer loop builds a library — memory learning, not gradient step on the LLM each time.

STaR / self-training from traces

Model generates reasoning traces; filter to those that reach correct answers; fine-tune on survivors. Risk: confirmation bias and error propagation — needs strong filters and fresh held-out tasks.

RLHF / DPO / RLAIF on agent data

Log preferred vs rejected trajectories (human or AI judge) → preference optimization. Best when actions are structured (tool JSON) and rewards are clear; expensive to label at scale — often subsample critical failures only.

Evaluation — agents ≠ chat benchmarks
Benchmark / family What it stresses Note
SWE-bench (and variants) Real repo issues, patch + tests CodeAct + sandbox; good end-to-end verifier
WebArena / visual web agents Multi-step site interaction Fragile to UI change; high LLM cost
τ-bench / tool-centric sims API tool sequences, stateful env Closer to prod tool calling
AgentBench-style suites Multi-domain tool + reasoning Useful regression; not one number for “AGI”
Your own golden tasks Tenant workflows, ACL, latency SLAs Ship gate — 20–50 tasks often enough

Track tool-call accuracy, recovery after tool error, and cost per success — not just final string match.

Safety & abuse in learning loops
  • Poisoned observations — RAG or web tool returns “ignore policy”; do not write that into semantic memory without sanitization.
  • Feedback hijacking — thumbs-down spam or adversarial edits to preference data.
  • Overfitting to eval — tuning prompts on the same 50 tasks until memoration — rotate holdouts.
  • Credential leakage into training — scrub logs before FT; see security implementation.
Production playbook
Default safe stack
  1. Bounded control graph + structured tool calling.
  2. Log trajectories with verifiers and tenant id.
  3. Improve prompts and tool docs from failure clusters (human review).
  4. Promote verified skills to semantic memory.
  5. Quarterly (or triggered) LoRA/DPO on filtered logs — full regression on golden tasks.
When to avoid weight updates
  • Low volume or noisy rewards; regulated domains without audit trail.
  • You can fix the issue with retrieval, memory, or a clearer tool schema instead.
  • Multi-tenant data mixing — train per tenant or use federated / segregated stores.
Chooser
  • User says “remember this” → semantic memory row + confirm UI; not automatic FT.
  • Same failure twice → episodic retrieval + prompt fix before fine-tune.
  • Verifiable domain (code, SQL) → Reflexion + tests; then skill library.
  • Scale quality → offline DPO on verified wins/losses; keep base model frozen between releases.
  • Research autonomy → RL / self-training only with sandbox + human gates — treat as experiment, not deploy default.
