DevOps — containers

Why containers exist

A container packages your app, runtime, and libraries into one runnable unit that behaves the same on your laptop, CI, and production. You stop fighting “Python 3.9 on the server but 3.11 locally.” The host runs a container engine; your image carries the rest.

Core ideas
Image vs container

An image is the read-only template (layers built from a Dockerfile or buildpack). A container is a running instance of that image. You build once, run many containers from the same tag.

Dockerfile habits
  • Pin base image tags (python:3.11-slim, not bare latest in prod).
  • Copy dependency file first, install, then copy code — better layer cache on rebuild.
  • Run as non-root user when the platform allows it.
  • One main process per container (API server or worker, not both unless you know why).
Registry

Push images to a registry (Docker Hub, GHCR, ECR, GCR/Artifact Registry). Production pulls by digest or immutable tag. CI builds the image, scans it optionally, pushes, then deploy references that tag — CI/CD.

Where containers run
Docker Compose (local / small)

Compose wires app + database + redis on one machine for dev or tiny demos. Good for head start; not a full production HA story by itself.

PaaS (managed runtime)

Cloud Run, Fly.io, Render, Heroku-class: you provide an image or git repo; the platform scales and routes HTTP. Lowest ops for solo builders; less control over networking and GPU attach.

Kubernetes (K8s)

Kubernetes schedules many containers across a cluster, handles restarts, rolling updates, and service discovery. Reach for it when you have multiple services, team scale, or strict HA — not for day-one “hello API” unless the org already runs K8s. ML inference (vLLM) often lands on K8s or a managed variant at scale — Kubernetes concepts, then serving.

ML & GPU notes

GPU training containers need CUDA-compatible base images and drivers on the host (or managed ML instances). Inference images bundle vLLM/TGI or your FastAPI wrapper — register the same digest you tested in staging (registry).

Chooser

First HTTP service → Dockerfile + one PaaS or Compose. Team product → registry + CI build + staging deploy. Many microservices or on-prem → learn K8s basics after containers feel normal.
