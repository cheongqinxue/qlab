MLOps — monitoring & drift

Training metrics ≠ production health

Val loss on a frozen set tells you how the model behaved then. In production you care about latency, errors, cost, user outcomes, and whether incoming data still looks like training data. Monitoring closes the loop in the lifecycle.

Always track (any ML service)
Service level
  • Request rate, p95/p99 latency, error rate (4xx/5xx), timeout rate.
  • GPU/CPU utilization and queue depth on inference pools.
  • Cost per day (tokens, GPU hours) — tie to cloud billing labels.
Model proxies

Log prediction confidence or score distributions when available. For classifiers, track predicted class histograms; sudden shifts often precede quality drops. Compare weekly to a baseline snapshot from launch week.

Drift
Data drift

Data drift means input distribution changed — new vocabulary, image styles, or document formats — while labels may still be defined the same way. Detect with embedding distance, PSI on features, or simple stats (length, language id). Drift alone does not prove quality fell, but it triggers re-eval on golden sets.

Concept drift

Concept drift means the relationship between inputs and correct outputs changed (policy update, product redesign, seasonality). You need delayed labels, human review, or business KPIs to see it; input-only monitors miss it.

LLM, RAG & agents
LLM chat & completion
  • Output length, refusal rate, average logprob if logged (privacy permitting).
  • Thumbs down / escalation rate; sample for human review.
  • Repeat detection (same boilerplate) — can indicate mode collapse in fine-tuned policies.
RAG
  • Retrieval Recall@k on logged queries with periodic human qrels (metrics).
  • Empty retrieval rate, average similarity score, citation presence rate.
  • Faithfulness failures — answers not supported by retrieved chunks (grounding).
Agents

Tool call success rate, steps per task, recovery after tool errors, and fraction of runs hitting step or token caps (reliability). Trace ids linking user session → retrieval → model version (registry version in logs).

Alerts & response

Alert on SLO breaches (latency, error spike) and on slow-burn drift (weekly compare to baseline). Runbook: rollback registry stage first if a bad deploy correlates with the timestamp; retrain only when data or policy truly changed. Post-incident, add a case to the golden eval set so CI catches it next time (pipelines).

Chooser

Batch scoring → monitor batch job success and score distributions. Online API → latency + errors + weekly golden replay. RAG product → retrieval hit rate + faithfulness sample daily. Agents → tool failures and cost per successful task.
