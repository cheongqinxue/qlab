Fusion, diversity & ranking

Where this fits in the stack

First-stage retrieval returns hundreds of candidate chunks from one or more sources (dense vectors, BM25, metadata filters, multiple rewritten queries). Fusion merges those lists into a single ordering without assuming scores are comparable. Diversity reduces near-duplicate passages so the language model sees varied evidence. A cross-encoder reranker (or ColBERT rescore) then re-orders a short list using a slower, more accurate scorer. Fusion and diversity are cheap; reranking is expensive and runs only on tens of candidates.

Structured lookups (order ID, primary key) should bypass this stack entirely and call an API or SQL with authorization. Fusion optimizes unstructured knowledge bases where the user mentions prose, partial codes, or paraphrases.

Reciprocal Rank Fusion (RRF)
Why rank fusion instead of mixing raw scores

Dense cosine similarity and BM25 scores live on different scales and distributions. A weighted sum α·dense + (1−α)·sparse looks simple but requires tuning α on every corpus and breaks when you add a third list (for example a second dense model or a multi-query run). Reciprocal Rank Fusion ignores magnitudes and uses only each document’s rank in each list, which makes it the default way to merge hybrid retrieval in production RAG.

RRF formula and tuning

For each document d, sum contributions from every ranked list in which d appears:

$$\mathrm{RRF}(d) = \sum_{i \in \text{lists}} \frac{1}{k + \mathrm{rank}_i(d)}$$

Here ranki(d) is the 1-based rank of d in list i (missing documents contribute nothing). The constant k dampens the advantage of top-1 over top-20; values around 60 are common in literature and engines. Lower k puts more weight on top ranks; higher k flattens differences.

Typical pattern: retrieve 50–100 from dense ANN and 50–100 from BM25, fuse with RRF, take the top 50 fused IDs, then cross-encode down to 5–10 chunks for the prompt. Evaluate recall@k on a golden set when changing k or list depths; small shifts rarely matter if reranking is strong, but ID-heavy slices often need deeper BM25 lists.

Multi-query fusion

A single user question can be expanded into several search queries (LLM rewrite, sub-questions, or HyDE-style hypothetical text). Each query produces its own ranked list; RRF merges them so a chunk that appears high under multiple phrasings rises in the fused list. This helps vague questions without replacing hybrid lexical search: you still want BM25 in at least one list when error codes and product SKUs must match literally.

Maximal Marginal Relevance (MMR)
Purpose and formula

Top-k vector search often returns five chunks that say the same thing with slightly different wording. That wastes context window and can bias the model toward one narrow source. Maximal Marginal Relevance selects documents that stay relevant to the query while penalizing similarity to documents already chosen.

Greedy selection: start with the highest query similarity, then repeatedly pick the candidate that maximizes

$$\mathrm{MMR} = \arg\max_{d \in C \setminus S}\ \lambda\,\mathrm{Sim}(d,q) - (1-\lambda)\,\max_{s \in S} \mathrm{Sim}(d,s)$$

C is the candidate pool (often 50–100 after fusion), S is the set already selected, and Sim is usually cosine similarity between embeddings. λ near 1 favors relevance; lower λ pushes diversity. MMR runs on embeddings already computed for search, so it is inexpensive compared with a cross-encoder.

MMR vs reranking vs deduplication

Use deduplication (hash or SimHash on normalized text) to drop exact and near-exact duplicates before the prompt. Use MMR when duplicates are paraphrases or overlapping chunks from the same manual. Use a cross-encoder reranker when the problem is wrong ordering among genuinely different passages, not redundancy. Many pipelines run RRF → optional MMR on the fused top 30 → cross-encoder on 20 → final 5. Skipping MMR is fine when chunks are small and non-overlapping by construction.

Query-side techniques (before fusion)
HyDE — Hypothetical Document Embeddings

HyDE is a query-time trick from the retrieval literature (Gao et al., “Precise Zero-Shot Dense Retrieval without Relevance Labels”). Embedding models are trained so that a passage that would answer a question is similar to other answer-like passages in the corpus. A bare question is often short and phrased differently from how your policies and runbooks are written, so its vector can land far from the right chunks even when the knowledge exists in the index.

HyDE closes that gap by asking a language model to write a hypothetical document: a few sentences that look like an excerpt from a real KB article, not a chat reply to the user. You embed that hypothetical text with the same bi-encoder you use for indexed chunks, run approximate nearest neighbor search with that vector, and treat the retrieved passages as normal RAG context for the final answer. The final answer should still be generated from retrieved text with citations; the hypothetical paragraph is thrown away after search and must not be shown to the user as fact.

Step-by-step at query time: (1) user question arrives; (2) LLM prompt such as “Write a short passage that would answer this question using typical internal documentation tone” (no tools, no browsing); (3) embed the hypothetical passage; (4) retrieve top‑k from the vector index; (5) optionally also retrieve with the embedded original question and fuse both lists with RRF so you do not rely on the hallucinated text alone; (6) rerank and pass real chunks to the answer model.

When it helps: vague or conversational queries (“how do I fix the payment thing?”), zero-shot search with no in-domain fine-tuning on the embedder, and corpora written in expository prose rather than question form. When it hurts: questions that hinge on exact identifiers (order IDs, error codes, legal citations), because the hypothetical passage may invent wrong codes and pull irrelevant chunks; high-stakes domains where a wrong retrieve is worse than empty retrieval; and latency-sensitive paths where an extra LLM call per query is unacceptable.

HyDE is not the same as query rewriting (still a question-shaped string), step-back prompting (a broader question), or generating the final user-facing answer. It is only a synthetic search query document. Guard it with low-temperature generation, length limits, and a fallback to plain question embedding when first-pass retrieval confidence is already high.

Query rewriting and decomposition

Rewriting expands acronyms, fixes typos, or adds domain synonyms before search. Decomposition splits multi-part questions (“compare plan A and plan B refunds”) into sub-queries, each retrieved and fused with RRF. Both increase recall when a single embedding of the raw user message is a poor match to indexed prose.

Step-back and metadata-aware routing

Step-back prompting asks the model for a broader question first (“what is our refund policy in general?”) and retrieves for that plus the specific user question, then fuses lists. Separately, a lightweight router can send queries with extracted order IDs, account numbers, or ticket IDs to transactional APIs while sending everything else to hybrid RAG. That router is not fusion; it prevents treating structured identifiers as semantic search terms.

Stronger lexical and late-interaction options
Learned sparse retrieval (SPLADE and similar)

Classical BM25 uses hand-crafted term weights. Learned sparse models (SPLADE is the common example) produce a sparse high-dimensional vector per query and document so expansion terms are learned rather than fixed. Engines that support sparse vectors (or hybrid sparse+dense in one index) can replace or complement BM25 in the same RRF merge. The trade-off is another model to serve at index and query time versus better recall on keyword-heavy enterprise text.

Native hybrid in the database

Some vector databases fuse dense and sparse inside the engine (Weaviate hybrid, Qdrant sparse vectors, OpenSearch neural hybrid). You may still apply RRF externally when combining more than two lists (multi-query, ColBERT rescore path, separate title vs body indexes). Treat engine hybrid as one input list into your wider fusion layer when the pipeline grows.

ColBERT and cross-encoder (after fusion)

RRF and MMR operate on candidate IDs and cheap scores. ColBERT MaxSim rescores with token-level interaction; a cross-encoder scores each query–passage pair jointly. These fix ordering among fused candidates but do not replace hybrid first stage for literal codes. Details and model choice: representations, retrieval stages.

Index-time techniques that affect ranking
Contextual retrieval (document context prepended to chunks)

Before embedding, prepend a short situating context to each chunk (for example title, section, and summary generated once per document). Chunks then embed with their place in the document explicit, which reduces false positives where the same sentence appears in unrelated policies. This is an indexing change, not a fusion formula, but it pairs well with RRF because both dense and sparse lists benefit from clearer chunk text.

Parent–child and hierarchical indexes

Store small chunks for retrieval but return a larger parent span to the language model (or retrieve summaries at one level and leaf chunks at another, then fuse with RRF). This improves ranking when the answer needs surrounding sentences that would not fit a tiny chunk boundary. See chunking for layout patterns.

Choosing and measuring a stack
Practical default and when to add complexity

Start with bi-encoder ANN plus BM25, merged with RRF, cross-encoder rerank top 50 to top 5, and metadata filters for ACLs. Add MMR if eval shows redundant chunks in context. Add multi-query or HyDE when recall@50 is low on paraphrase-heavy questions but lexical slices are already strong. Add SPLADE or ColBERT when recall@10 plateaus after chunking and hybrid tuning. Always slice metrics by query type (IDs and codes vs prose) so optimizations do not average away regressions.

Offline metrics: recall@k and nDCG on labeled chunks per query; online: citation coverage, abstention rate, and task success on replayed support tickets. Formulas for rank metrics live on the metrics sheet.

Linear score fusion (when it still appears)

Some teams normalize dense and sparse scores to zero mean and unit variance on a dev sample, then use a weighted sum. This can work for a frozen two-list hybrid inside one vendor API but does not generalize cleanly when lists change length or when a third retriever is added. Prefer RRF for multi-list merges unless the platform documents a single calibrated hybrid score you cannot bypass.
