Testing — concepts & objectives

Why test

Automated tests give you confidence to change code without guessing whether production will break. They turn requirements into executable checks, catch regressions before users do, and document how the system is supposed to behave. Tests do not prove absence of bugs — they reduce risk cheaply and repeatedly.

Testing objectives (what “good” looks like)
  • Correctness — outputs match spec for known inputs (including error paths).
  • Regression prevention — a fixed bug stays fixed; CI reruns the same checks on every merge.
  • Design feedback — hard-to-test code often signals tight coupling; tests push you toward clear seams.
  • Release gates — green tests are a minimum bar before deploy; ML adds eval thresholds (see ML testing).
  • Living documentation — a well-named test reads like an example; keep it in sync with behavior, not wishful comments.
Major test categories
Type Scope Typical speed
Unit One function, class, or module in isolation Milliseconds
Integration Two or more real pieces wired together (DB, HTTP client, file I/O) Seconds
End-to-end (e2e) Full user or API journey through deployed or near-prod stack Minutes
Contract / API Request/response shape and status codes against a schema or golden file Fast to medium
Other labels you will hear

Smoke tests ask “does the app start and respond?” — minimal path after deploy. Regression tests re-run a suite that previously failed or that guards a critical feature. Acceptance tests check business scenarios (often manual or BDD-style) before sign-off. Performance and load tests measure latency and capacity under stress — see performance & load.

Vocabulary
  • Fixture — reusable setup (data, temp dirs, configured clients) shared across tests.
  • Assertion — the check that fails the test when behavior is wrong.
  • Mock / stub / fake — test doubles that replace slow or external dependencies; details on Python & pytest.
  • Flaky test — passes and fails without code changes (timing, shared state, network); fix or quarantine — do not ignore.
  • Coverage — which lines ran during tests; useful for gaps, not a quality score by itself.
  • Test isolation — each test should not depend on order or leftover state from another test.
Manual vs automated

Exploratory manual testing still finds UX and edge cases automation misses. Automate what is repeatable and high value: core logic, APIs, regressions, and CI gates. Reserve manual passes for new features, visual design, and one-off production validation.

Chooser — I changed…

Pure logic or refactor → unit tests. New DB query or external API wiring → integration test (real test DB or container when feasible). New user flow or deploy path → smoke or e2e on staging. Prompt or model behavior → golden eval set (ML testing), not only unit tests.
